LEZIONE 01 · Fondamenti

Cos’è Node.js

Prima di iniziare: le parole della lezione

Runtime
Ambiente che esegue un programma e gli fornisce servizi: Node.js è il runtime, JavaScript è il linguaggio del codice.
V8
Motore JavaScript usato anche da Chrome: esegue JavaScript e può compilarlo in codice macchina. Il codice non viene prima tradotto in C++.
Frontend e backend
Il frontend è la parte con cui interagisce l’utente, spesso nel browser; il backend gestisce richieste, regole e dati sul server.
API, I/O e thread
API significa interfaccia di programmazione: funzioni e regole con cui usare un componente. I/O significa input/output, come leggere un file o scambiare dati in rete. Un thread è un flusso di esecuzione di istruzioni.
DOM e framework
Il DOM è la rappresentazione della pagina HTML manipolabile dal browser. Un framework è una struttura software che organizza lo sviluppo: Express sarà il framework web di questa guida.

Node.js è un ambiente di esecuzione JavaScript fuori dal browser. Usa il motore V8 e mette a disposizione API lato server: file system, rete, processi e altro. Non è un linguaggio diverso da JavaScript, né un framework web.

  • Browser: dispone di DOM, window, interfaccia grafica e Web API.
  • Node.js: dispone di process, file system, server HTTP e API di sistema. Non esiste un DOM di default.
  • Event loop: permette di coordinare molte operazioni I/O senza bloccare il thread JavaScript mentre si aspetta un risultato. Questo non significa che qualsiasi calcolo sia automaticamente parallelo.
console.log('Ciao da Node.js');
console.log('Versione:', process.version);
console.log('Sistema operativo:', process.platform);

Esempio pratico. Un server può avviare la lettura di un file e nel frattempo continuare a gestire altre richieste. Se invece esegue un ciclo CPU molto pesante sul thread principale, le altre richieste possono rallentare.

Chi fa cosa, e perché

Nella metafora della banca del testo, lo sportellista è il thread JavaScript: riceve le richieste e avvia le operazioni. Il lavoro che richiede attesa può essere affidato al sistema operativo o ad altri componenti di Node; quando è pronto, il codice riprende a elaborarne il risultato. Questo permette di servire più utenti senza tenere fermo lo sportello per ogni attesa.

Il server è il programma che offre un servizio; il computer che lo ospita viene spesso chiamato anch’esso server. Il client è il programma che lo contatta, ad esempio un browser. Node può eseguire anche strumenti da terminale, senza creare alcun server. V8 esegue JavaScript, Node fornisce le API, il sistema operativo gestisce risorse come file e rete.

Un altro esempio guidato

// ambiente.cjs — avvio: node ambiente.cjs
console.log('JavaScript:', [1, 2, 3].map(n => n * 2));
console.log('API Node:', process.version);
console.log('DOM disponibile?', typeof document);

Come leggerlo e risultato atteso. La prima riga stampa un array con 2, 4, 6; map trasforma ogni elemento. La seconda legge la versione del runtime. La terza stampa undefined: in un normale script Node non c’è una pagina da manipolare.

Pratica attuale e precisazioni. Node offre anche API condivise con il web, per esempio fetch per richieste HTTP in uscita. “Fuori dal browser” non significa che tutte le API del browser siano assenti: il DOM, però, non è fornito automaticamente.

Prova tu. Indica chi esegue JavaScript, chi mostra la pagina e chi legge un file dal disco. Risposta: il motore nel runtime, il browser e le API di Node con il sistema operativo.

Definizioni complete: dal termine al comportamento

Ambiente di esecuzione
Un runtime combina un motore che esegue il linguaggio con API e regole per interagire con l’ambiente. JavaScript descrive variabili, funzioni e oggetti; Node aggiunge accesso a file, rete e processi. Lo stesso linguaggio può quindi avere capacità diverse nel browser e sul server.
Processo e thread
Un processo è un’istanza di programma con memoria e risorse proprie. Un thread è un flusso di esecuzione al suo interno. Il codice JavaScript principale usa un thread, ma Node può coordinare lavoro del sistema operativo e thread ausiliari: “single-threaded” non descrive ogni attività del processo.
I/O e carico CPU
I/O indica scambio di dati con disco, rete o altre risorse; spesso comporta attesa. Un carico CPU usa invece tempo di calcolo, per esempio comprimere o trasformare grandi quantità di dati. Rendere una funzione async non sposta automaticamente il calcolo su un altro thread.

Verifica la comprensione

Perché una funzione async con un ciclo di un miliardo di iterazioni rallenta il server?

Leggi la spiegazione

Il calcolo resta sul thread JavaScript: async cambia il valore restituito, non il luogo in cui il corpo viene eseguito.

Installazione e ambiente

Prima di iniziare: le parole della lezione

LTS
Long-Term Support: linea di versioni mantenuta nel tempo con correzioni e aggiornamenti di sicurezza.
Terminale, shell e CLI
Il terminale mostra l’interfaccia testuale; la shell, per esempio PowerShell, interpreta i comandi; una CLI è un programma utilizzabile tramite comandi.
PATH e directory di lavoro
PATH è l’elenco di cartelle in cui la shell cerca gli eseguibili. La directory di lavoro è la cartella da cui un comando viene eseguito.
Editor e REPL
Un editor modifica i file di codice. Una REPL legge un’espressione, la esegue, stampa il risultato e attende il comando successivo.

Installa una versione LTS attualmente supportata dal sito ufficiale di Node.js. Il corso originale mostra versioni 14 e 16: sono riferimenti storici, non versioni da installare oggi. Usa un editor come Visual Studio Code; le estensioni sono facoltative.

node --version
npm --version
mkdir corso-node
cd corso-node

Crea index.js e lancialo:

node index.js

Esempio aggiuntivo: per aprire la console interattiva basta eseguire node, scrivere 2 + 2 e uscire con .exit. Controllo: se node non viene riconosciuto, riapri il terminale e verifica l'installazione e il PATH.

Chi fa cosa, e perché

L’installer rende disponibile node; npm è il gestore di pacchetti normalmente distribuito insieme a Node. Visual Studio Code serve a scrivere e salvare i file, mentre il terminale avvia il runtime. Scrivere codice nell’editor non lo esegue: occorre salvarlo e passare il file a node.

Alcune estensioni dell’editor propongono frammenti di codice, detti snippet. Sono facoltative e non installano né Node né Express. Tieni aperta nel terminale la cartella che contiene il tuo script: un file esistente in un’altra cartella può risultare “non trovato”.

Un altro esempio guidato

# PowerShell: un comando per riga
node --version
npm --version
Get-Location
node -e "console.log('Installazione riuscita')"

Come leggerlo e risultato atteso. --version chiede la versione; Get-Location mostra la cartella attuale; -e esegue il breve programma passato come testo e stampa Installazione riuscita. Per avviare un file con spazi nel nome usa node "primo esempio.cjs".

Pratica attuale e precisazioni. Scegli una linea LTS ancora supportata dalla tabella ufficiale delle release. Le versioni 14 e 16 della registrazione sono fuori supporto. Non occorre installare pacchetti globali per iniziare.

Prova tu. Apri una nuova shell dopo l’installazione e ripeti i controlli. Se node funziona ma npm è bloccato da PowerShell, prova npm.cmd --version prima di modificare impostazioni del sistema.

Definizioni complete: dal termine al comportamento

Terminale, shell e directory
Il terminale mostra una sessione; la shell interpreta i comandi. La directory corrente determina come si risolvono molti percorsi relativi. L’editor modifica il sorgente, mentre node esegue il file salvato: un file aperto nell’editor non viene eseguito automaticamente.
PATH e installazione
PATH è l’elenco di directory in cui la shell cerca i programmi. “node non riconosciuto” riguarda spesso installazione o PATH, non la sintassi del tuo script. Verifica node --version e npm --version nello stesso terminale che userai per il corso.
Versione e riproducibilità
La versione del runtime stabilisce quali API sono disponibili. Registra la versione usata e scegli una release supportata compatibile con il progetto. Una versione più recente sul tuo computer non garantisce che il computer di un compagno esegua lo stesso codice.

Il file esiste ma node non lo trova: cosa controlli?

Leggi la spiegazione

Directory corrente, percorso passato al comando, nome ed estensione del file; poi la versione del runtime.

LEZIONE 03 · Fondamenti

Prime righe di codice

Prima di iniziare: le parole della lezione

Script e processo
Uno script è un file di istruzioni; un processo è l’istanza del programma avviata dal sistema operativo.
Funzione e argomento
Una funzione raggruppa istruzioni richiamabili. Un argomento è un valore passato quando la si invoca; il parametro è il nome che lo riceve.
const, let e confronto stretto
const impedisce di riassegnare una variabile; let permette di riassegnarla. === confronta senza conversione automatica di tipo.

Un programma Node.js è un normale file .js eseguito dal terminale. La sintassi JavaScript resta valida, salvo le API specifiche del browser.

// index.js
const numero = 3;
if (numero < 3) console.log('Minore di 3');
else if (numero === 3) console.log('Uguale a 3');
else console.log('Maggiore di 3');
for (let i = 0; i < 3; i++) console.log('Giro', i);

node index.js

Esempio aggiuntivo: console.log(typeof document) stampa undefined in un normale processo Node.js. Prima di avviare il programma ricordati di salvare il file.

Chi fa cosa, e perché

Il comando node index.js carica il file salvato sul disco e ne esegue il codice dall’alto verso il basso. Il nome index è una convenzione, non una parola speciale. Un programma senza server, timer attivi o altre attività in attesa normalmente termina quando finisce il lavoro.

console.log scrive nel terminale del processo. Non aggiorna una pagina web. Un errore di sintassi impedisce di interpretare il codice; un errore durante l’esecuzione può avvenire dopo che alcune istruzioni sono già state eseguite. Leggi il file e il numero di riga indicati nel messaggio.

Un altro esempio guidato

// argomenti.cjs — avvio: node argomenti.cjs Anna
const nome = process.argv[2] ?? 'visitatore';
function saluta(persona) {
  return `Ciao, ${persona}!`;
}
console.log(saluta(nome));

Come leggerlo e risultato atteso. process.argv è l’array degli argomenti del processo: le prime due posizioni riguardano eseguibile e script. La posizione 2 contiene Anna. L’operatore ?? usa il valore a destra se quello a sinistra è null o undefined. La funzione restituisce il saluto, poi console.log lo stampa.

Pratica attuale e precisazioni. Usa l’estensione completa nei comandi: rende chiaro quale file avvii. Nei prossimi esempi .cjs rende esplicito CommonJS, mentre .mjs rende espliciti gli ES Modules. La lezione 5 spiega i due sistemi.

Prova tu. Avvia lo script senza nome: deve stampare Ciao, visitatore!. Poi modifica il valore predefinito, salva e rilancialo.

Definizioni complete: dal termine al comportamento

Dichiarazione e assegnazione
Dichiarare crea un binding, assegnare gli associa un valore. let permette riassegnazioni; const le vieta, ma non rende immutabile un oggetto. Con const persona = {nome: "Ada"} puoi modificare persona.nome, ma non assegnare un nuovo oggetto a persona.
Valore, tipo e coercizione
Il tipo appartiene al valore. Stringhe e numeri possono sembrare uguali quando stampati, ma "2" + 3 produce "23" mentre 2 + 3 produce 5. Converti e valida gli input esplicitamente; Number("abc") produce NaN e va controllato.
Funzione, return e log
Una funzione riceve argomenti ed esegue un compito. return consegna il risultato al chiamante; console.log lo visualizza e non lo sostituisce. Senza return esplicito una normale funzione restituisce undefined. Separa il calcolo dalla stampa per riutilizzarlo e testarlo.

Verifica la comprensione

Una funzione stampa 10 ma il chiamante riceve undefined: perché?

Leggi la spiegazione

console.log non è return. La funzione deve restituire il valore se il chiamante deve riutilizzarlo.

LEZIONE 04 · Fondamenti

Oggetti globali e process

Prima di iniziare: le parole della lezione

Globale e ambito del modulo
Un globale è disponibile senza importazione. L’ambito del modulo contiene nomi validi solo in quel file: le variabili dichiarate con const non diventano automaticamente proprietà globali.
process e variabile d’ambiente
process descrive il processo Node. Una variabile d’ambiente è un valore di configurazione esterno al codice, letto con process.env.
Callback e timer
Una callback è una funzione passata a un’altra funzione perché la richiami. Un timer pianifica una callback dopo un intervallo minimo, senza garantirne l’istante esatto.

In Node.js trovi globali come console, setTimeout, process e globalThis. Il corso usa anche __dirname, __filename, require e module: sono disponibili nei moduli CommonJS, non allo stesso modo nei moduli ESM.

// index.cjs (CommonJS)
console.log(__dirname);
console.log(__filename);
console.log(process.cwd());
console.log(process.env.NODE_ENV ?? 'non definito');
setTimeout(() => console.log('Dopo 200 ms'), 200);

// index.mjs (ES modules): alternativa moderna
import { fileURLToPath } from 'node:url';
import { dirname } from 'node:path';
const filename = fileURLToPath(import.meta.url);
const directory = dirname(filename);
console.log(directory);

NODE_ENV è una convenzione: non garantisce da sola che il codice sia sicuro o configurato correttamente. Evita di stampare in log l'intero process.env, perché può contenere segreti.

Chi fa cosa, e perché

__dirname indica la cartella del modulo CommonJS che lo contiene; __filename ne indica il percorso completo. process.cwd() indica invece la cartella da cui hai avviato il processo. Se importi un file da una sottocartella, il suo __dirname cambia, ma cwd() resta quello del processo, salvo modifiche esplicite.

require carica un modulo e module ne rappresenta il contesto CommonJS: non sono normali globali universali. globalThis è il nome standard dell’oggetto globale, ma condividere dati tramite globali rende più difficile capire chi li modifica.

Un altro esempio guidato

// configurazione.cjs — node configurazione.cjs
const porta = Number(process.env.PORT ?? 3000);
if (!Number.isInteger(porta) || porta < 1 || porta > 65535) {
  console.error('PORT deve essere un intero tra 1 e 65535');
  process.exitCode = 1;
} else {
  console.log('Porta configurata:', porta);
}

Come leggerlo e risultato atteso. Senza configurazione stampa 3000. I valori di process.env sono normalmente stringhe: Number converte il testo, il controllo scarta valori non validi. exitCode = 1 comunica un esito di errore quando il processo termina.

Pratica attuale e precisazioni. Negli ES Modules delle linee Node moderne sono disponibili import.meta.dirname e import.meta.filename per moduli locali. La conversione con fileURLToPath(import.meta.url) mostrata sopra resta utile per compatibilità. Riferimento: documentazione ESM.

Prova tu. In PowerShell esegui $env:PORT = "4000" e poi lo script: deve leggere 4000. Con Remove-Item Env:PORT rimuovi la variabile dalla shell corrente.

Definizioni complete: dal termine al comportamento

Oggetto globale e ambito del modulo
globalThis identifica l’oggetto globale. Le variabili dichiarate nel livello superiore di un modulo restano normalmente nel suo ambito e non diventano proprietà globali. Evitare stato globale riduce dipendenze implicite tra file e richieste.
Argomenti del processo
process.argv contiene percorso del runtime, file avviato e argomenti successivi. Gli argomenti sono stringhe: un limite passato dal terminale va convertito e controllato. process.cwd() restituisce la directory di avvio, che può differire da quella dello script.
Configurazione e uscita
process.env legge variabili d’ambiente come stringhe o undefined. Usa valori di default e validazione; non stampare segreti nei log. process.exitCode imposta il codice finale consentendo al lavoro pendente di terminare, mentre process.exit() può interrompere operazioni ancora in corso.

Verifica la comprensione

PORT contiene "3000": è già un numero?

Leggi la spiegazione

No. Le variabili d’ambiente sono stringhe: converti e verifica un intero nell’intervallo ammesso.

LEZIONE 05 · Moduli e I/O

Creare moduli

Prima di iniziare: le parole della lezione

Modulo, importazione ed esportazione
Un modulo è un’unità di codice con un proprio ambito. Esportare significa rendere un valore utilizzabile da altri file; importare significa ottenere quel valore.
CommonJS ed ESM
CommonJS usa require e module.exports. ESM significa ECMAScript Modules: è il sistema standard JavaScript basato su import ed export.
Destructuring e cache
Il destructuring estrae proprietà da un oggetto. Una cache conserva un risultato per riutilizzarlo: i moduli caricati vengono normalmente riutilizzati nelle importazioni successive dello stesso processo.

Dividere un programma in moduli rende il codice più leggibile, testabile e riutilizzabile. Nel corso si usa soprattutto CommonJS (require, module.exports).

Esempio CommonJS:

// saluti.cjs
function saluta(nome) { return `Ciao, ${nome}!`; }
module.exports = { saluta };

// main.cjs
const { saluta } = require('./saluti.cjs');
console.log(saluta('Anna'));

Alternativa ES Modules:

// saluti.mjs
export const saluta = nome => `Ciao, ${nome}!`;
// main.mjs
import { saluta } from './saluti.mjs';
console.log(saluta('Marco'));

Nota: l'importazione può eseguire il codice al livello superiore del modulo; evita effetti collaterali inattesi all'import.

Chi fa cosa, e perché

Nel testo, separare nomi e funzioni dal file principale serve a dare a ogni file una responsabilità. Il modulo dei nomi contiene i dati; il modulo delle utilità contiene funzioni; il file principale li collega. Una variabile rimane privata finché non viene esportata.

In CommonJS module.exports = saluta esporta direttamente la funzione; module.exports = { saluta } esporta un oggetto che la contiene. Nel secondo caso const { saluta } = require(...) estrae quella proprietà. Scrivere solo exports = qualcosa non sostituisce module.exports. Inoltre importare un array non ne crea automaticamente una copia: lo stesso oggetto esportato può essere condiviso fra moduli.

Un altro esempio guidato

// prezzi.mjs
export function conIva(prezzo, aliquota = 0.22) {
  return prezzo * (1 + aliquota);
}

// main.mjs — salva questa parte in un secondo file
import { conIva } from './prezzi.mjs';
console.log(conIva(100).toFixed(2));
// Avvio: node main.mjs

Come leggerlo e risultato atteso. prezzi.mjs definisce il calcolo, main.mjs lo usa e stampa 122.00. ./ significa “rispetto al file che importa”; ../ sale alla cartella superiore. toFixed(2) produce una stringa con due decimali.

Pratica attuale e precisazioni. Per nuovi esempi puoi scegliere ESM; CommonJS resta supportato e non è automaticamente deprecato. Specifica "type": "module" per usare ESM nei file .js, oppure usa .mjs. Per le importazioni ESM relative indica l’estensione. Evita di cambiare sistema a metà esempio senza adattare il resto.

Prova tu. Esporta anche senzaIva, importala nel file principale e verifica che da 122 torni circa a 100. I numeri decimali JavaScript possono avere approssimazioni.

Definizioni complete: dal termine al comportamento

Interfaccia pubblica
Un modulo raggruppa responsabilità e rende disponibili solo gli elementi esportati. Chi lo importa dipende dalla sua interfaccia, non dai dettagli interni. Separare una funzione di validazione dal server permette di testarla senza aprire una porta.
CommonJS ed ES modules
CommonJS usa require e module.exports; ESM usa import ed export. .cjs dichiara CommonJS e .mjs dichiara ESM; per file .js conta la configurazione del package. Nei percorsi relativi ESM esplicita l’estensione. Non mescolare le due sintassi senza capire le regole di interoperabilità.
Stato condiviso e dipendenze circolari
Importare un modulo non equivale a creare ogni volta un’istanza indipendente del suo stato. Una lista modificabile esportata può essere condivisa dai consumatori. Se A importa B e B importa A, l’inizializzazione diventa difficile da seguire: estrai le responsabilità comuni in un terzo modulo.

Leggi la spiegazione

LEZIONE 06 · Moduli e I/O

Moduli built-in: OS e PATH

Prima di iniziare: le parole della lezione

Built-in, OS e architettura
Built-in significa integrato nel runtime. OS è il sistema operativo. L’architettura indica la famiglia di istruzioni dell’ambiente, per esempio x64 o arm64.
Percorso assoluto e relativo
Un percorso assoluto parte dalla radice o dall’unità; uno relativo dipende da una cartella di riferimento.
Byte e separatore
Un byte è un’unità di informazione di otto bit. Il separatore divide i segmenti di un percorso: Windows e sistemi Unix possono usarne di diversi.

I moduli integrati sono già disponibili e non si installano con npm. node:os fornisce dati sul sistema; node:path gestisce percorsi in modo multipiattaforma.

// os-path.cjs
const os = require('node:os');
const path = require('node:path');
console.log(os.platform(), os.arch());
console.log('RAM totale (GiB):', (os.totalmem() / 1024**3).toFixed(1));
const file = path.join(__dirname, 'dati', 'utenti.json');
console.log(file);
console.log(path.basename(file)); // utenti.json
console.log(path.extname(file));  // .json

Esempio aggiuntivo: path.resolve('dati', 'utenti.json') crea un percorso assoluto a partire dalla directory di lavoro corrente; path.join combina segmenti e normalizza il percorso. Non concatenare a mano separatori per costruire percorsi.

Chi fa cosa, e perché

os.type() descrive il sistema, os.release() la sua release, os.freemem() la memoria libera e os.totalmem() quella totale, in byte. Dividere per 1024 ** 3 dà gibibyte, abbreviati GiB, anche quando un esempio usa genericamente l’etichetta GB.

path.join unisce segmenti e normalizza separatori e ..; path.resolve costruisce un percorso assoluto; basename estrae il nome finale e extname l’estensione. Nessuna di queste funzioni crea cartelle o verifica che il file esista: manipolano percorsi come testo.

Un altro esempio guidato

// percorsi.cjs — node percorsi.cjs
const path = require('node:path');
const os = require('node:os');
const destinazione = path.join(os.tmpdir(), 'corso-node', 'log.txt');
console.log(path.parse(destinazione));
console.log('Estensione:', path.extname(destinazione));

Come leggerlo e risultato atteso. os.tmpdir() restituisce la cartella temporanea del sistema. path.parse restituisce un oggetto con radice, cartella, nome completo, estensione e nome senza estensione. L’ultima riga stampa .txt; nessun file viene scritto.

Pratica attuale e precisazioni. Il prefisso node: rende esplicito che stai usando un modulo integrato. Normalizzare un percorso non autorizza l’accesso: un percorso costruito da input utente deve anche essere controllato rispetto alle cartelle consentite.

Prova tu. Confronta path.resolve("dati") con path.join(__dirname, "dati") avviando lo script da un’altra cartella.

Modulo built-in
Un modulo built-in viene distribuito con Node e non richiede npm install. Il prefisso node: rende esplicita questa origine, per esempio node:path e node:os. Un pacchetto di terze parti ha invece un ciclo di aggiornamento e dipendenze separati.

Queste funzioni manipolano stringhe: non verificano che il file esista.

Windows e sistemi Unix hanno convenzioni diverse. Usa le API dei percorsi per costruire nomi portabili. Normalizzare un percorso non autorizza l’accesso: se proviene dall’utente, verifica anche che resti nella directory consentita, considerando link simbolici e vincoli dell’applicazione.

File system: sync e async

Prima di iniziare: le parole della lezione

File system, encoding e Buffer
Il file system organizza file e cartelle. L’encoding stabilisce come convertire byte in testo: UTF-8 è una scelta comune. Un Buffer contiene byte, non una stringa JavaScript.
Sincrono e asincrono
Una chiamata sincrona restituisce il risultato prima di proseguire e può bloccare il thread. Una chiamata asincrona avvia il lavoro e ne rende disponibile il risultato successivamente.
Promise, async e await
Una Promise rappresenta un esito futuro, riuscito o fallito. Una funzione async restituisce una Promise; await sospende quella funzione finché la Promise si risolve o fallisce.
try/catch
try delimita operazioni che possono fallire; catch riceve l’errore e permette di gestirlo.

fs consente di leggere e scrivere file. Le operazioni *Sync bloccano il thread JavaScript fino al termine; per server e attività I/O frequenti preferisci le API asincrone.

// file.cjs
const fs = require('node:fs');
fs.writeFileSync('nota.txt', 'Prima riga\n');
fs.appendFileSync('nota.txt', 'Seconda riga\n');
console.log(fs.readFileSync('nota.txt', 'utf8'));

Stessa operazione con Promise:

// file-async.mjs
import { readFile, writeFile, appendFile } from 'node:fs/promises';
try {
  await writeFile('nota.txt', 'Prima riga\n');
  await appendFile('nota.txt', 'Seconda riga\n');
  const testo = await readFile('nota.txt', 'utf8');
  console.log(testo);
} catch (errore) {
  console.error('Errore file:', errore.message);
}

Precisazione: writeFile sovrascrive per impostazione predefinita; appendFile aggiunge in fondo. Non mischiare letture e scritture concorrenti dello stesso file senza coordinarle.

Chi fa cosa, e perché

La versione a callback del corso segue la convenzione error-first: il primo parametro contiene l’eventuale errore, il secondo il risultato. Senza utf8, una lettura restituisce normalmente un Buffer. Se devi leggere due file e poi scrivere il contenuto combinato, devi aspettare entrambe le letture: posizionare la scrittura sotto le chiamate asincrone non basta.

Le Promise evitano di annidare molte callback. Due await consecutivi mantengono l’ordine delle operazioni; Promise.all può attendere più letture indipendenti. Non rende sicure scritture concorrenti sullo stesso file. Le API sincrone possono andare bene per piccoli script o preparazione iniziale; dentro una route rallentano anche gli altri utenti.

Un altro esempio guidato

// lettura.cjs — crea prima nota.txt nella cartella di avvio
const fs = require('node:fs');
console.log('1. Avvio lettura');
fs.readFile('nota.txt', 'utf8', (errore, testo) => {
  if (errore) {
    console.error('Lettura fallita:', errore.code);
    return;
  }
  console.log('3. Contenuto:', testo);
});
console.log('2. Il programma può proseguire');

Come leggerlo e risultato atteso. Le righe 1 e 2 vengono stampate prima della callback. Se il file manca, leggi tipicamente ENOENT, codice che segnala un percorso inesistente. return impedisce di usare testo dopo l’errore. Il percorso relativo viene risolto dalla directory di lavoro.

Pratica attuale e precisazioni. Per nuovo codice asincrono l’interfaccia node:fs/promises con await è spesso più leggibile. Le callback restano valide. Usa stream, spiegati alla lezione 14, se non vuoi tenere in memoria un file intero.

Prova tu. Rinomina il file di input e osserva il ramo di errore; poi ripristinalo. Verifica che la scrittura con writeFile sostituisca davvero il contenuto precedente prima di usarla su dati importanti.

Definizioni complete: dal termine al comportamento

Buffer e codifica
Un file contiene byte. Una Buffer rappresenta dati binari; una codifica come UTF-8 interpreta i byte come testo. readFile senza codifica restituisce una Buffer, con utf8 restituisce una stringa. Applicare JSON.parse ha senso solo dopo aver letto testo contenente JSON valido.
Sync, callback e Promise
Le API sincrone bloccano il thread chiamante fino al risultato. Quelle a callback consegnano errore e dato a una funzione; node:fs/promises restituisce Promise da attendere. L’attesa asincrona aiuta un server a rispondere ad altri utenti, ma non elimina il costo del disco.
Errori e scritture concorrenti
Un file può mancare, essere inaccessibile o contenere dati corrotti. Distingui ENOENT dagli altri errori invece di restituire sempre una lista vuota. Due operazioni read-modify-write possono sovrascriversi: un file JSON non fornisce automaticamente transazioni o coordinamento tra processi.

Creare un server HTTP

Prima di iniziare: le parole della lezione

HTTP e server HTTP
HTTP è il protocollo con cui un client invia richieste e riceve risposte. Un server HTTP resta in ascolto e applica una funzione a ogni richiesta ricevuta.
Porta e localhost
Una porta identifica un punto di accesso di rete di un processo. localhost indica il computer locale; 3000 è una porta di sviluppo convenzionale.
req, res e route
req è l’oggetto della richiesta; res costruisce la risposta. Una route è una regola che collega metodo e percorso a una funzione di gestione.
Header e status
Gli header sono metadati della richiesta o risposta. Lo status è il codice numerico che ne descrive l’esito; 200 indica successo, 404 risorsa non trovata.

Node include node:http, utile per capire il funzionamento di un server senza librerie esterne.

// server.cjs
const http = require('node:http');
const server = http.createServer((req, res) => {
  if (req.url === '/' && req.method === 'GET') {
    res.writeHead(200, { 'Content-Type': 'text/plain; charset=utf-8' });
    return res.end('Benvenuto!');
  }
  res.writeHead(404, { 'Content-Type': 'text/plain; charset=utf-8' });
  res.end('Non trovato');
});
server.listen(3000, () => console.log('http://localhost:3000'));

Avvia con node server.cjs, visita http://localhost:3000 e prova /manca per il 404.

Concetto chiave: req contiene i dati della richiesta, res costruisce la risposta. Per il routing complesso, Express riduce il codice ripetitivo.

Chi fa cosa, e perché

http.createServer crea il server e registra la callback, ma non apre da solo la porta. listen lo mette in ascolto. Il callback di listen viene eseguito all’avvio; quello di createServer viene richiamato per ogni richiesta.

res.writeHead imposta status e header; res.write può inviare una parte del contenuto; res.end conclude la risposta, eventualmente con l’ultimo contenuto. Dopo aver risposto, un return evita di cadere nel ramo 404. Un server resta attivo perché ha risorse di rete in ascolto: fermalo con Ctrl+C.

Un altro esempio guidato

// ora.cjs — node ora.cjs
const http = require('node:http');
const server = http.createServer((req, res) => {
  const url = new URL(req.url, 'http://localhost');
  if (req.method === 'GET' && url.pathname === '/ora') {
    res.writeHead(200, { 'Content-Type': 'application/json; charset=utf-8' });
    return res.end(JSON.stringify({ ora: new Date().toISOString() }));
  }
  res.writeHead(404, { 'Content-Type': 'text/plain; charset=utf-8' });
  res.end('Percorso non trovato');
});
server.listen(3000, '127.0.0.1', () => console.log('Apri http://127.0.0.1:3000/ora'));

Come leggerlo e risultato atteso. new URL separa il percorso dalla query: anche /ora?formato=iso ha pathname /ora. La data è convertita in testo ISO; JSON.stringify produce il body JSON. Un’altra route riceve 404. Il server dell’esempio ascolta solo sull’interfaccia locale.

Pratica attuale e precisazioni. Nel modulo HTTP nativo req.url comprende la query string; un confronto diretto con "/" non riconosce /?x=1. EADDRINUSE indica spesso una porta già occupata: chiudi il processo precedente o scegli un’altra porta.

Prova tu. Apri /ora due volte e confronta i timestamp; prova poi un percorso inesistente e controlla lo status negli strumenti di rete del browser.

Definizioni complete: dal termine al comportamento

Server, socket e porta
Un server HTTP ascolta connessioni su un indirizzo e una porta. Una porta identifica un servizio sul sistema; EADDRINUSE indica che la combinazione richiesta è già occupata. Ascoltare solo su 127.0.0.1 limita l’accesso alla macchina locale.
Richiesta e risposta come stream
req espone metodo, URL e header ed è leggibile come stream per il body. res consente di scrivere header e dati e deve essere conclusa. Il body può arrivare in più chunk: non assumere che un evento data contenga tutto il messaggio.
Protocollo e responsabilità applicativa
node:http offre primitive del protocollo, non decide le tue route o la validità dei dati. Imposta status e Content-Type coerenti e concludi anche i rami di errore. Un client lasciato senza risposta resta in attesa finché una delle parti interrompe la connessione.

Riavvio automatico: nodemon e watch

Prima di iniziare: le parole della lezione

Watcher e riavvio
Un watcher osserva modifiche ai file. Il riavvio termina il processo precedente e ne avvia uno nuovo, rieseguendo il programma dall’inizio.
Dipendenza di sviluppo
Strumento necessario per lavorare sul progetto, ma non per il normale funzionamento del server distribuito.
Hot reload
Aggiornamento del codice o dell’interfaccia senza un completo riavvio del contesto: non coincide con il semplice riavvio di Node.

Il problema mostrato nelle prime lezioni è dover riavviare manualmente Node dopo ogni modifica. nodemon lo risolve; le versioni moderne di Node offrono anche --watch.

# soluzione senza pacchetto aggiuntivo
node --watch server.js
# alternativa con dipendenza di sviluppo
npm install --save-dev nodemon
npx nodemon server.js

Esempio aggiuntivo: nel package.json imposta "dev": "node --watch server.js", poi esegui npm run dev. Per la produzione usa normalmente uno script di avvio stabile e una gestione appropriata del processo, non un watcher di sviluppo.

Chi fa cosa, e perché

Nel testo Nodemon risolve la sequenza “salva, Ctrl+C, rilancia”. Osserva i file e riavvia il processo. Non aggiorna automaticamente una scheda del browser: devi fare una nuova richiesta per vedere il comportamento del server aggiornato.

Il riavvio ricrea variabili, array e contatori. Se inserisci una persona nell’array RAM e poi salvi un file mentre il watcher è attivo, quella persona può sparire: il nuovo processo riparte dai dati iniziali. Non è un errore di POST, ma una conseguenza dell’assenza di persistenza.

Un altro esempio guidato

// osserva.cjs — avvio: node --watch osserva.cjs
console.log('Nuovo processo:', process.pid);
console.log('Avviato:', new Date().toISOString());
setInterval(() => console.log('Ancora attivo'), 5000);

Come leggerlo e risultato atteso. Il timer ripetuto mantiene attivo il programma. Cambia il messaggio e salva: il watcher riavvia lo script, cambia il timestamp e normalmente cambia anche il PID, cioè l’identificatore del processo. Con Ctrl+C termini la sessione di osservazione.

Pratica attuale e precisazioni. Il watch integrato è stabile nelle versioni moderne di Node ed evita una dipendenza per il caso base; Nodemon resta utile per configurazioni più articolate. Consulta Node --watch. Né l’uno né l’altro sostituisce un sistema di gestione del processo in produzione.

Prova tu. Aggiungi una variabile contatore e osserva che torna al valore iniziale a ogni riavvio. Distingui il riavvio del server dal refresh del browser.

Watch e riavvio
Un watcher osserva file e avvia nuovamente il processo quando cambiano. Il riavvio elimina lo stato in memoria: non è un aggiornamento trasparente di ogni variabile. Se una lista scompare dopo un salvataggio, potrebbe essere il comportamento previsto del tuo archivio in memoria.
nodemon e modalità watch
nodemon è uno strumento aggiuntivo configurabile; node --watch è una modalità del runtime. La disponibilità e i dettagli dipendono dalla versione. Scegli un solo meccanismo di riavvio per evitare processi duplicati e conflitti sulla stessa porta.
Sviluppo e distribuzione
Un watcher facilita il ciclo modifica-prova, ma non sostituisce test, gestione dei log o recupero dagli errori in produzione. Se il programma scrive file osservati, escludili quando opportuno per evitare una catena continua di riavvii.

Event loop e non-blocking

Prima di iniziare: le parole della lezione

Call stack ed event loop
Il call stack tiene traccia delle funzioni in esecuzione. L’event loop coordina quando eseguire callback di timer, rete e altre operazioni, quando lo stack permette di farlo.
Concorrenza e parallelismo
Concorrenza significa gestire più attività nello stesso periodo; parallelismo significa eseguirle davvero nello stesso istante su risorse distinte.

Un thread pool è un gruppo di thread riutilizzati per certi lavori. libuv è la libreria su cui Node basa parte della gestione di I/O, event loop e thread pool.
Microtask e CPU-bound
Le microtask includono reazioni alle Promise e vengono elaborate in specifici punti dell’esecuzione. CPU-bound indica lavoro dominato dal calcolo, anziché dall’attesa di dati.

L'event loop orchestra l'esecuzione del codice e dei callback quando le operazioni asincrone terminano. Non confondere asincronia, parallelismo e multithreading: il codice JavaScript di un processo Node normalmente gira su un thread principale, mentre parte del lavoro I/O è delegata al sistema operativo o al thread pool.

console.log('A');
setTimeout(() => console.log('C (timer)'), 0);
Promise.resolve().then(() => console.log('B (microtask)'));
console.log('D');
// A, D, B, C

Esempio aggiuntivo: await readFile(...) lascia spazio ad altre operazioni durante l'attesa; un ciclo while che occupa la CPU per molti secondi blocca comunque l'event loop. Per calcoli pesanti valuta worker thread o processi separati.

Chi fa cosa, e perché

Nella banca, lo sportellista non si moltiplica: coordina le pratiche. Allo stesso modo il JavaScript principale esegue un pezzo di codice alla volta; il sistema operativo può gestire attese di rete e il thread pool alcune operazioni, fra cui molte operazioni sui file. Dire “ogni richiesta ha un thread” oppure “Node usa un solo thread in assoluto” descrive male il funzionamento.

Nell’esempio A/D/B/C, le due stampe sincrone vengono prima della reazione della Promise; il timer non può interrompere il codice già in esecuzione. setTimeout(fn, 0) significa pianificare appena possibile dopo la soglia del timer, non chiamare subito fn. La parola async non sposta un ciclo pesante su un altro thread.

Un altro esempio guidato

// attese.mjs — node attese.mjs
import { setTimeout as pausa } from 'node:timers/promises';
async function lavoro(nome, ms) {
  await pausa(ms);
  return nome;
}
const risultati = await Promise.all([
  lavoro('lento', 80),
  lavoro('veloce', 20)
]);
console.log(risultati);

Come leggerlo e risultato atteso. Le due attese vengono avviate prima di attenderne l’esito insieme. Il risultato è ["lento", "veloce"]: Promise.all preserva l’ordine degli input, non quello di completamento. Se una Promise fallisce, l’attesa complessiva fallisce; le altre operazioni non sono cancellate automaticamente.

Pratica attuale e precisazioni. Per calcoli pesanti considera worker_threads, cioè thread che eseguono altro JavaScript, oppure processi separati. L’ordine di casi più complessi con setImmediate e timer dipende dal contesto: evita regole assolute ricavate da una sola prova. Vedi event loop di Node.

Prova tu. Sostituisci Promise.all con due await consecutivi e confronta il tempo complessivo: nel primo caso è vicino all’attesa maggiore, nel secondo alla somma, con variazioni dovute alla schedulazione.

Definizioni complete: dal termine al comportamento

Stack, code e callback
Il call stack contiene le funzioni JavaScript in esecuzione. Una callback pronta deve aspettare un’occasione per essere eseguita; non interrompe arbitrariamente una funzione in corso. Le continuazioni delle Promise vengono gestite come microtask, distinti dalle fasi dell’event loop.
Timer e disponibilità
Un timeout indica una soglia di attesa, non un appuntamento esatto. Un ciclo lungo sul thread principale ritarda anche una callback già pronta. Non basare la correttezza del programma sull’ordine assoluto tra timer e I/O indipendenti.
Concorrenza e parallelismo
Concorrenza significa far progredire più attività nello stesso intervallo di tempo; parallelismo significa eseguirle contemporaneamente su risorse diverse. I/O asincrono permette concorrenza senza un thread JavaScript per richiesta. Per calcoli pesanti valuta worker dedicati e misura il costo di comunicazione.

EventEmitter e programmazione a eventi

Prima di iniziare: le parole della lezione

Evento, emittente e listener
Un evento è una notifica con un nome ed eventuali dati. L’emittente la produce; un listener è la funzione registrata per reagire.
EventEmitter e istanza
EventEmitter è la classe di Node per notifiche a eventi. Un’istanza, creata con new, è un oggetto con i propri listener.
on, once, emit e off
on registra un listener; once lo registra per una sola esecuzione; emit emette; off rimuove un listener specifico.

EventEmitter fornisce un modello per emettere eventi e registrare ascoltatori. È utile per notifiche interne, strumenti e flussi applicativi.

// eventi.cjs
const { EventEmitter } = require('node:events');
const bus = new EventEmitter();
bus.on('utenteCreato', utente => console.log('Creato:', utente.nome));
bus.once('primoAccesso', () => console.log('Solo una volta'));
bus.emit('utenteCreato', { nome: 'Luca' });
bus.emit('primoAccesso');
bus.emit('primoAccesso'); // nessun secondo log

Attenzione: emit() invoca sincronamente gli ascoltatori registrati. EventEmitter non crea automaticamente code persistenti né rende le funzioni asincrone. Gestisci con cura gli eventi error.

Chi fa cosa, e perché

L’ordine conta: registra gli ascoltatori prima di emettere l’evento. Un normale EventEmitter non conserva un evento per chi si iscrive dopo. Gli argomenti passati dopo il nome in emit vengono consegnati ai listener nello stesso ordine.

La registrazione non chiama subito la funzione; emit chiama invece in modo sincrono gli ascoltatori già registrati. Se un listener avvia lavoro asincrono, quel lavoro ha la propria durata: l’emittente non aspetta automaticamente tutte le Promise. Il modello serve per disaccoppiare una notifica dalle reazioni, ma non garantisce consegna persistente fra processi.

Un altro esempio guidato

// ascoltatori.cjs — node ascoltatori.cjs
const { EventEmitter } = require('node:events');
const eventi = new EventEmitter();
function registra(id, totale) {
  console.log(`Ordine ${id}: ${totale} euro`);
}
eventi.on('ordine', registra);
eventi.emit('ordine', 7, 25);
eventi.off('ordine', registra);
eventi.emit('ordine', 8, 30);

Come leggerlo e risultato atteso. Viene stampato solo l’ordine 7. Per rimuovere un listener serve il riferimento alla stessa funzione: una nuova arrow function, anche con lo stesso corpo, è un altro oggetto funzione. Nell’esempio iniziale il secondo primoAccesso non stampa nulla perché il listener era registrato con once.

Pratica attuale e precisazioni. L’evento speciale error richiede attenzione: emetterlo senza listener può terminare il processo. Anche registrare listener senza rimuoverli quando non servono più può accumulare memoria. Le API a eventi restano attuali; Promise e async/await risolvono un problema diverso.

Prova tu. Aggiungi due listener allo stesso evento e verifica l’ordine delle stampe; poi emetti prima di registrarli per osservare che l’evento non viene riprodotto.

Definizioni complete: dal termine al comportamento

Evento, emitter e listener
Un evento segnala che qualcosa è accaduto. Un emitter mantiene listener associati a nomi e li chiama quando l’evento viene emesso. Il produttore non deve conoscere ogni consumatore, ma entrambi devono concordare nome e dati dell’evento.
Ordine e durata dei listener
EventEmitter chiama normalmente i listener in modo sincrono durante emit, nell’ordine di registrazione. on registra un ascolto persistente, once lo rimuove dopo il primo evento. Un listener lento può quindi rallentare chi emette; “a eventi” non significa automaticamente asincrono.
Errori e pulizia
L’evento error ha un trattamento speciale: senza un listener può far terminare il processo. Rimuovi listener quando non servono più, soprattutto se trattengono riferimenti a oggetti. Una crescita continua degli ascoltatori può essere un indizio di una perdita di memoria.

LEZIONE 14 · HTTP e runtime

Stream: dati a pezzi

Prima di iniziare: le parole della lezione

Chunk, stream e buffering
Un chunk è una porzione di dati. Uno stream permette di leggerne o scriverne una sequenza; il buffering conserva temporaneamente porzioni in memoria.
Readable, Writable, Duplex e Transform
Readable produce dati; Writable li riceve; Duplex può fare entrambe le cose; Transform è uno stream duplex che trasforma ciò che riceve, come una compressione.
Backpressure e pipeline
La backpressure rallenta il produttore quando il consumatore non tiene il passo. Una pipeline collega più stream e ne coordina completamento ed errori.

Uno stream gestisce dati in modo incrementale, senza necessariamente caricare l'intero contenuto in memoria. È utile per file grandi, download e trasferimenti HTTP.

// copia.cjs
const fs = require('node:fs');
const { pipeline } = require('node:stream/promises');
(async () => {
  try {
    await pipeline(
      fs.createReadStream('origine.txt'),
      fs.createWriteStream('copia.txt')
    );
    console.log('Copia completata');
  } catch (errore) { console.error(errore.message); }
})();

Esempio aggiuntivo: con gli stream si può inviare al client un file di grandi dimensioni mentre lo si legge. pipeline() propaga in modo più affidabile errori e chiusura delle risorse rispetto a un semplice pipe() usato senza gestione degli errori.

Chi fa cosa, e perché

readFile rende disponibile il file completo; createReadStream lo fornisce a porzioni. Nel corso gli eventi data mostrano i chunk: la loro dimensione non coincide necessariamente con una riga o con un messaggio applicativo. Un file può quindi essere letto senza tenerlo tutto in memoria contemporaneamente.

highWaterMark controlla una soglia del buffer interno, non un limite rigido alla memoria totale. pipe collega una sorgente a una destinazione e gestisce il flusso; pipeline aiuta a coordinare anche errori e chiusura. Le richieste e risposte HTTP di Node sono a loro volta stream.

Un altro esempio guidato

// dimensione.mjs — crea prima origine.txt; node dimensione.mjs
import { createReadStream } from 'node:fs';
let byte = 0;
try {
  for await (const chunk of createReadStream('origine.txt')) {
    byte += chunk.length;
  }
  console.log('Byte letti:', byte);
} catch (errore) {
  console.error('Lettura fallita:', errore.message);
}

Come leggerlo e risultato atteso. for await...of consuma le porzioni disponibili senza dover scrivere a mano i listener data ed end. Senza encoding i chunk sono Buffer e length conta byte: lettere accentate UTF-8 possono occupare più di un byte.

Pratica attuale e precisazioni. Usa pipeline per copie o trasformazioni fra stream; l’iterazione asincrona è utile quando devi elaborare ogni porzione. Sono approcci complementari. Riferimento: API Stream di Node. Un errore durante uno streaming HTTP può arrivare quando parte della risposta è già stata inviata.

Prova tu. Crea un file con caratteri accentati e confronta il numero di byte con il numero di caratteri del testo. Non sommare chunk.toString().length come se fossero sempre la stessa misura.

Definizioni complete: dal termine al comportamento

Chunk e tipi di stream
Uno stream trasferisce dati in parti invece di richiedere tutto il contenuto in memoria. Readable produce dati, Writable li riceve, Duplex fa entrambe le cose, Transform converte ciò che legge in ciò che scrive. I confini dei chunk non coincidono necessariamente con righe o messaggi.
Backpressure
Se il produttore è più veloce del consumatore, occorre limitarne il flusso per evitare accumulo. Questo feedback si chiama backpressure. Quando write restituisce false, il produttore deve rispettare il segnale e attendere drain prima di continuare a scrivere.
Pipeline e completamento
pipeline collega stream e coordina errori e terminazione. Un errore a metà trasferimento non equivale a un risultato completo. Per un file di destinazione parziale valuta una strategia di pulizia; non annunciare successo prima che la pipeline sia completata.

Richieste HTTP: struttura e metodi

Prima di iniziare: le parole della lezione

URL, host e percorso
L’URL identifica una risorsa: schema, host, eventuale porta, percorso e query. L’host identifica il computer o servizio di destinazione; il percorso identifica la risorsa presso quel servizio.
Body, Content-Type e Accept
Il body è il contenuto del messaggio. Content-Type descrive il formato inviato; Accept indica i formati di risposta accettati dal client.
HTTPS e TLS
HTTPS è HTTP protetto da TLS, che cifra il trasporto e autentica normalmente il server tramite certificati.
Idempotenza
Un’operazione è idempotente se ripeterla produce lo stesso effetto finale sullo stato desiderato. Non implica risposte identiche a ogni chiamata.

Una richiesta HTTP include metodo, percorso, header e opzionalmente un body. Una risposta include codice di stato, header e body. HTTP è un protocollo richiesta-risposta; HTTPS aggiunge la protezione TLS.

Metodo Uso tipico Esempio
GET Leggere GET /api/persone
POST Creare POST /api/persone
PUT Sostituire/aggiornare completamente PUT /api/persone/1
PATCH Modificare parzialmente PATCH /api/persone/1
DELETE Eliminare DELETE /api/persone/1

Codici frequenti: 200 OK, 201 creato, 204 riuscito senza contenuto, 400 richiesta errata, 404 non trovato, 500 errore del server.

curl -i http://localhost:3000/

Esempio aggiuntivo: un browser che apre un URL invia normalmente una GET; per inviare JSON e scegliere altri metodi puoi usare curl, Postman o il fetch() del frontend.

Chi fa cosa, e perché

Il browser invia la richiesta, il server la interpreta e costruisce la risposta. Aprire una pagina può produrre diverse richieste: documento HTML, foglio di stile, JavaScript, immagini e favicon. Un errore sulla favicon non significa necessariamente che la route principale abbia fallito.

I metodi esprimono l’intenzione: GET legge, POST richiede un’elaborazione o una creazione, PUT sostituisce, PATCH modifica parzialmente, DELETE elimina. Una risposta 404 significa che il server ha risposto ma non ha trovato quella risorsa; una connessione rifiutata significa invece che non sei riuscito a contattarlo su quell’indirizzo e porta.

Un altro esempio guidato

GET /api/persone?limite=2 HTTP/1.1
Host: localhost:3000
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"dati":[{"id":1,"nome":"Anna"}]}

Come leggerlo e risultato atteso. È uno schema didattico di richiesta e risposta HTTP/1.1, non un file JavaScript da avviare. La riga iniziale identifica metodo e destinazione; la riga vuota separa header e body. Il codice 200 appartiene alla risposta, non alla richiesta.

Pratica attuale e precisazioni. GET è definito come metodo sicuro, cioè con semantica di lettura; PUT e DELETE sono idempotenti. PATCH non è automaticamente idempotente. POST non rende segreto il body: per proteggere il trasporto serve HTTPS. Vedi i metodi HTTP.

Prova tu. Apri gli strumenti sviluppatore del browser, scheda Rete/Network: identifica richiesta, status, Content-Type e contenuto della risposta. Non confondere il testo di un errore JSON con lo status HTTP.

Definizioni complete: dal termine al comportamento

Semantica HTTP
Metodo e risorsa esprimono l’intento della richiesta; status e rappresentazione descrivono il risultato. GET legge, POST sottopone dati a una risorsa, PUT sostituisce lo stato desiderato di una risorsa, DELETE ne richiede la rimozione. Il significato concreto deve essere documentato nel contratto.
Stateless e sessione
HTTP non mantiene automaticamente uno stato applicativo tra richieste. Cookie o token permettono di associare richieste a un contesto, ma l’applicazione deve validarli. Stateless non significa che un backend non possa conservare dati: significa che il protocollo non ricorda da solo il tuo flusso.
Sicurezza e idempotenza
Un metodo safe è definito per non richiedere modifiche di stato; idempotente significa che ripetere la stessa richiesta ha lo stesso effetto desiderato. GET è safe e idempotente; PUT e DELETE sono idempotenti ma modificano stato. Un retry automatico di POST può creare duplicati senza un meccanismo dedicato.

Introduzione a Express

Prima di iniziare: le parole della lezione

Express e app
Express è il framework che organizza la gestione HTTP sopra Node. express() crea un’applicazione, qui chiamata app.
Routing, handler ed endpoint
Il routing seleziona la funzione in base a metodo e percorso. L’handler gestisce la richiesta. Un endpoint è un punto di accesso dell’API, generalmente identificato da metodo e URL.
Middleware
Funzione nella catena di gestione di una richiesta: può eseguire controlli, preparare dati, rispondere o passare il controllo alla funzione successiva.

Express è un framework web che semplifica server, middleware e routing. Non sostituisce Node: vi gira sopra.

mkdir mini-express
cd mini-express
npm init -y
npm install express@5

// server.cjs
const express = require('express');
const app = express();
app.get('/', (req, res) => res.send('Home Express'));
app.get('/saluti/:nome', (req, res) => {
  res.json({ messaggio: `Ciao ${req.params.nome}` });
});
app.listen(3000, () => console.log('http://localhost:3000'));

Esegui node server.cjs. Esempio aggiuntivo: visita /saluti/Anna. Il callback della route riceve req (richiesta) e res (risposta).

Chi fa cosa, e perché

require("express") carica il pacchetto installato. express() costruisce l’app; app.get registra una route GET; app.listen crea e avvia il server HTTP. Express estende gli oggetti di Node con strumenti come res.send, res.json e req.params.

res.status(201) imposta lo status ma non invia da solo la risposta. res.send e res.json la inviano e normalmente la concludono. La concatenazione res.status(...).json(...) funziona perché status restituisce lo stesso oggetto risposta. Invia una sola risposta per richiesta.

Un altro esempio guidato

// mini.cjs — npm install express@5; poi node mini.cjs

  return res.status(200).json({ servizio: 'attivo' });
});
app.use((req, res) => {
  res.status(404).json({ errore: 'Percorso non trovato' });
});
app.listen(3000, '127.0.0.1', () => console.log('Server pronto sulla porta 3000'));

Come leggerlo e risultato atteso. GET /salute restituisce 200 e JSON. Una richiesta non gestita arriva al middleware finale e riceve 404. Il middleware senza percorso si applica a tutte le richieste che lo raggiungono. Deve stare dopo le route, altrimenti risponde prima di esse.

Pratica attuale e precisazioni. Questa guida usa Express 5 per i nuovi esempi. Alcune forme dei percorsi del vecchio Express 4 sono cambiate: per una 404 generale il middleware finale senza percorso evita il vecchio app.all("*"). Fonte: migrazione a Express 5.

Prova tu. Aggiungi GET /versione prima della 404 e restituisci process.version. Prova anche POST /salute: avere una route GET non registra automaticamente una POST.

Una route associa metodo e percorso a uno o più handler. Un handler legge la richiesta, esegue il lavoro e risponde oppure passa il controllo. La registrazione avviene all’avvio; la callback viene invocata per ogni richiesta corrispondente.

Servire file statici

Prima di iniziare: le parole della lezione

File statico e directory pubblica
Un file statico viene inviato senza generare il contenuto da un template a ogni richiesta. La directory pubblica contiene i file che scegli di rendere raggiungibili dai client.
Mount path e sendFile
Il mount path è il prefisso URL a cui colleghi un middleware. res.sendFile invia uno specifico file, normalmente indicato con percorso assoluto o con una directory root.
HTML, CSS e JavaScript client
HTML descrive la struttura della pagina; CSS il suo aspetto; il JavaScript client viene eseguito dal browser dopo il caricamento.

I file statici (HTML, CSS, immagini e JavaScript client) possono essere serviti direttamente da una directory con express.static.

// server.cjs
const express = require('express');

app.use(express.static(path.join(__dirname, 'public')));
app.listen(3000);

Chi fa cosa, e perché

express.static restituisce un middleware: Express lo esegue sulle richieste che arrivano a quel punto. Con app.use(express.static(...)), un file public/stile.css si richiede come /stile.css, senza scrivere public nell’URL. Un index.html può essere servito automaticamente per la directory.

Il corso usa anche homepage.html, about.html, contatti.html e una pagina 404 con sendFile. La cartella fisica e il percorso web non devono coincidere: puoi esporre i file sotto /assets. “Statico” riguarda come il server produce la risposta: un file JavaScript statico può comunque rendere interattiva la pagina.

Un altro esempio guidato

// Dentro l'app Express CommonJS, prima della 404 finale

app.get('/about', (req, res, next) => {
  res.sendFile(path.join(cartella, 'about.html'), errore => {
    if (errore) next(errore);
  });
});

Come leggerlo e risultato atteso. Crea public/about.html con un titolo e un paragrafo. /about invia quel file; un eventuale public/stile.css è raggiungibile a /assets/stile.css. next(errore) passa un errore di invio alla gestione degli errori.

Pratica attuale e precisazioni. Il solo invio di un HTML già scritto non è SSR dinamico: il rendering server viene approfondito nella prossima lezione. Usa un percorso legato al modulo per non dipendere dalla cartella di avvio; esponi solo file destinati al pubblico.

Prova tu. Collega un foglio CSS da about.html con href="/assets/stile.css". Crea anche una 404 e inviala con res.status(404).sendFile(...), gestendo gli errori di invio.

Il browser può riutilizzare una copia in cache in base agli header. Se modifichi un file mantenendo lo stesso URL, il client potrebbe avere ancora la versione precedente. Nomi di asset legati al contenuto e politiche di cache coerenti aiutano a distinguere risorse nuove e vecchie.

Rendering significa costruire la vista. SSR, Server-Side Rendering, la costruisce sul server; CSR, Client-Side Rendering, la costruisce nel browser usando JavaScript.
Template engine ed escaping
Un template engine combina un modello di pagina con dati. L’escaping trasforma caratteri speciali per visualizzarli come testo anziché interpretarli come markup.

Il corso distingue due modalità: API, che restituiscono normalmente dati come JSON, e SSR, in cui il server genera HTML per il browser. Sono approcci combinabili.

app.get('/api/profilo', (req, res) => {
  res.json({ id: 1, nome: 'Sara' });
});
app.get('/pagina', (req, res) => {
  res.type('html').send('<h1>Pagina generata dal server</h1>');
});

Esempio aggiuntivo: un frontend React può chiamare /api/profilo e costruire la vista nel browser; un'app SSR potrebbe invece renderizzare lato server un template con lo stesso profilo. In entrambi i casi serve gestire correttamente errori e dati in ingresso.

Chi fa cosa, e perché

Con un’API JSON il backend recupera e controlla i dati; il frontend decide come mostrarli. Con SSR il backend recupera i dati e genera anche l’HTML della vista, spesso usando un template engine. La scelta riguarda dove si prepara la pagina, non se esista o meno un database.

Le due modalità possono convivere: un sito serve pagine HTML e offre endpoint JSON per aggiornare singole parti. Un array restituito come JSON non si trasforma da solo in una tabella: serve codice client o un template. Analogamente, servire un file HTML senza modificarlo rimane semplice distribuzione di contenuto statico.

JSON come formato di scambio

Prima di iniziare: le parole della lezione

JSON e oggetto JavaScript
JSON, JavaScript Object Notation, è un formato di testo per dati. Un oggetto JavaScript è invece un valore già presente in memoria: le due cose non sono identiche.
Serializzazione e parsing
Serializzare significa convertire un valore in testo trasmissibile. Fare parsing significa analizzare il testo e ricostruire una struttura di dati.
Schema e validazione
Uno schema descrive campi, tipi e vincoli attesi. La validazione verifica che i dati rispettino quelle regole, dopo che il testo è stato interpretato.

JSON è un formato testuale con oggetti, array, stringhe, numeri, booleani e null. In Express res.json() serializza un oggetto JavaScript e imposta la risposta JSON.

app.use(express.json()); // interpreta richieste con body JSON
app.get('/api/prodotti', (req, res) => {
  res.json([{ id: 1, nome: 'Tastiera', prezzo: 45 }]);
});
app.post('/api/eco', (req, res) => {
  res.status(201).json({ ricevuto: req.body });
});

Esempio aggiuntivo: invia {"nome":"Mouse"} con header Content-Type: application/json. Sicurezza: il fatto che req.body sia stato interpretato come JSON non significa che i dati siano validi: controlla tipi, lunghezze e valori.

Chi fa cosa, e perché

res.json(oggetto) serializza il valore e imposta il formato della risposta. express.json() compie l’operazione opposta per le richieste con Content-Type JSON: legge il body e rende il valore disponibile come req.body. Non serve per poter inviare JSON con una GET; serve per leggere JSON in ingresso.

JSON usa doppi apici per chiavi e stringhe, non accetta commenti, funzioni o undefined. Una data JavaScript viene normalmente serializzata come stringa; un array può contenere oggetti, numeri e altri valori JSON. Il middleware non decide se un prezzo è positivo o se un nome è troppo lungo: sono regole applicative da verificare dopo.

Un altro esempio guidato

const testo = JSON.stringify(persona);
const ricostruita = JSON.parse(testo);
console.log(typeof testo);       // string
console.log(ricostruita.nome);   // Anna
console.log(persona === ricostruita); // false

Come leggerlo e risultato atteso. JSON.stringify crea testo; JSON.parse crea una nuova struttura dati. Il confronto finale è falso perché i due oggetti hanno identità diverse. Non passare a res.json una stringa già serializzata se vuoi trasmettere un oggetto: finiresti per inviare una stringa JSON.

Pratica attuale e precisazioni. Per un body JSON usa express.json({ limit: "32kb" }) prima delle route interessate; per form HTML tradizionali può servire express.urlencoded. Sono parser diversi. Distingui sintassi JSON malformata (400), body troppo grande (413) e errore interno (500).

Parametri della route

Prima di iniziare: le parole della lezione

Parametro di percorso e ID
Un parametro di percorso è un segmento variabile della route. Un ID è un identificatore della risorsa: può essere numerico oppure una stringa, secondo il modello dati.
find e valore assente
find restituisce il primo elemento che soddisfa una condizione; se nessuno la soddisfa restituisce undefined.
Conversione e intero sicuro
La conversione cambia il tipo di un valore. Un intero sicuro è rappresentabile senza perdita di precisione nel formato Number di JavaScript.

I parametri della route identificano una risorsa all'interno dell'URL. Nel percorso /api/persone/:id, il segmento :id è letto da req.params.id.

const persone = [{ id: 1, nome: 'Anna' }, { id: 2, nome: 'Luca' }];
app.get('/api/persone/:id', (req, res) => {
  const id = Number(req.params.id);
  if (!Number.isInteger(id)) return res.status(400).json({ errore: 'ID non valido' });
  const persona = persone.find(p => p.id === id);
  if (!persona) return res.status(404).json({ errore: 'Non trovata' });
  res.json(persona);
});

Esempio aggiuntivo: /api/persone/2 restituisce Luca; /api/persone/abc restituisce 400, mentre /api/persone/999 restituisce 404.

Chi fa cosa, e perché

Express riempie req.params usando i nomi preceduti da due punti. In /articoli/:categoria/:id puoi leggere req.params.categoria e req.params.id. La forma const { id } = req.params è destructuring, non una richiesta al database.

Se gli ID dell’array sono numeri, confrontare p.id === req.params.id fallisce perché "2" è una stringa. Convertire e validare risolve il problema. Non convertire però un ID testuale, per esempio un UUID, come se fosse numerico. Distingui ID scritto male (400) e ID valido che non esiste (404).

Un altro esempio guidato

// Frammento da inserire in un'app Express
app.get('/articoli/:categoria/:id', (req, res) => {
  const { categoria, id: testoId } = req.params;
  const id = Number(testoId);
  if (!/^[1-9]\d*$/.test(testoId) || !Number.isSafeInteger(id)) {
    return res.status(400).json({ errore: 'ID numerico positivo richiesto' });
  }
  res.json({ categoria, id });
});

Come leggerlo e risultato atteso. /articoli/node/12 restituisce categoria node e ID numerico 12. L’espressione regolare controlla che la stringa contenga solo cifre e inizi da 1 a 9; isSafeInteger controlla il numero. Questo endpoint dimostra il parsing e non verifica l’esistenza di un articolo.

Pratica attuale e precisazioni. Definisci una politica coerente: Number("1e2") vale 100, ma un ID composto solo da cifre può rifiutare quella notazione. Registra percorsi fissi come /persone/statistiche prima di /persone/:id, per non interpretare “statistiche” come ID.

Prova tu. Prova 12, abc, 0 e 1e2. Spiega perché il controllo numerico e la ricerca della risorsa rispondono a due domande diverse.

Parametro di percorso
In /persone/:id, id è una parte variabile dell’identità della risorsa. req.params contiene valori estratti dal percorso come stringhe. Il parametro non è una query né il body; scegli dove mettere un dato in base al suo ruolo nel contratto.
Conversione e validazione
Convertire non significa validare. parseInt("12abc") può produrre 12, accettando input ambiguo. Per un identificatore intero positivo puoi usare una forma testuale rigorosa e controllare Number.isSafeInteger dopo la conversione. Stabilisci anche se "01" è accettabile.

Un ID malformato giustifica una risposta 400; un ID valido che non identifica alcuna risorsa giustifica 404. Questa distinzione aiuta client e log. Non usare l’indice di un array come ID stabile: cancellazioni e riordinamenti cambiano le posizioni.

Query string e filtri

Prima di iniziare: le parole della lezione

Query string e filtro
La query string è la parte dell’URL dopo ?, composta da coppie chiave-valore separate da &. Un filtro seleziona elementi secondo una condizione.
Paginazione, limite e offset
La paginazione divide un insieme in parti. Il limite indica quanti elementi restituire; l’offset quanti saltarne dall’inizio.
filter e slice
filter crea un array con gli elementi che soddisfano una condizione. slice restituisce una porzione senza modificare l’array originale.

I parametri query seguono ? nell'URL: /api/persone?cerca=an&limite=5. In Express sono in req.query, che contiene input da considerare non attendibile.

app.get('/api/persone', (req, res) => {
  const cerca = String(req.query.cerca ?? '').toLowerCase();
  const limiteRaw = Number(req.query.limite ?? 10);
  const limite = Number.isInteger(limiteRaw)
    ? Math.min(Math.max(limiteRaw, 1), 100) : 10;
  const risultato = persone
    .filter(p => p.nome.toLowerCase().includes(cerca))
    .slice(0, limite);
  res.json(risultato);
});

Esempio aggiuntivo: la ricerca ?cerca=lu&limite=1 restituisce al massimo una persona il cui nome contiene lu. Per grandi dataset filtri e paginazione andrebbero applicati nel database, non all'array intero.

Chi fa cosa, e perché

Il parametro di percorso identifica tipicamente “quale persona”; la query descrive “quali persone, con quale filtro e limite”. /persone/2 e /persone?limite=2 hanno quindi significati diversi. req.query dipende dal parser configurato: non dare per scontato che ogni valore sia una stringa singola, soprattutto con parametri ripetuti.

Una ricerca per prefisso con startsWith("an") trova Anna ma non Gianna. Nell’esempio del manuale includes("an") cerca invece in qualsiasi posizione. Documenta quale comportamento scegli. Con una collezione vuota o nessun risultato, una risposta 200 con elenco vuoto è normalmente corretta.

Pratica attuale e precisazioni. Valida i tipi e limita le quantità permesse. Un semplice slice(0, limite) applica un limite, ma non realizza da solo una paginazione navigabile. Middleware: ordine e next

Prima di iniziare: le parole della lezione

Catena di middleware e next
La catena è la sequenza registrata nell’app. next() passa il controllo alla funzione successiva compatibile; next(err) attiva il percorso di gestione errori.
Autenticazione e autorizzazione
L’autenticazione verifica chi è il chiamante; l’autorizzazione verifica se può compiere quella specifica operazione.
Logging e gestione errori
Il logging registra eventi utili a capire il comportamento del programma. Un gestore errori traduce un problema in una risposta controllata.

Un middleware è una funzione che opera tra richiesta e risposta. Può leggere/modificare req, rispondere o passare il controllo con next(); l'ordine di registrazione conta.

app.use((req, res, next) => {
  console.log(req.method, req.path);
  next();
});
app.use(express.json());
app.get('/salute', (req, res) => res.json({ ok: true }));
app.use((req, res) => res.status(404).json({ errore: 'Route inesistente' }));

Esempio aggiuntivo: un middleware di autenticazione può controllare una sessione prima delle route private. Attenzione: se non invii una risposta e non chiami next(), la richiesta resta in sospeso. Un middleware di errore ha firma (err, req, res, next).

Chi fa cosa, e perché

Nel testo il middleware viene prima scritto nel file principale, poi esportato in un modulo e infine applicato solo a un prefisso. app.use("/api", fn) limita la funzione a quel gruppo; app.get("/profilo", controllo, handler) la lega a una route. Puoi passare più middleware o un array di funzioni.

Un middleware ha tre possibilità: risponde e si ferma, chiama next, oppure segnala un errore. next() non equivale a return: il codice dopo può ancora eseguire. Usa return next() quando vuoi terminare subito il ramo. Un middleware che stampa “accesso effettuato” non autentica realmente nessuno.

Un altro esempio guidato

// Frammento: middleware specifico per una route
function richiediFormatoJson(req, res, next) {
  if (!req.is('application/json')) {
    return res.status(415).json({ errore: 'Invia application/json' });
  }
  return next();
}
app.post('/api/eco', richiediFormatoJson, express.json(), (req, res) => {
  res.json({ ricevuto: req.body });
});
// Evita di registrare anche un'altra POST /api/eco prima di questa.

Come leggerlo e risultato atteso. Il controllo legge il Content-Type e può rispondere 415, formato non supportato. Se passa, il parser interpreta JSON e l’handler risponde. L’ordine è controllo del formato → parser → handler; l’esempio assume che un parser globale precedente non abbia già letto il body.

Pratica attuale e precisazioni. Con Express 5 una Promise rigettata da un handler async restituito viene inoltrata alla gestione errori. Gli errori in callback scollegate richiedono ancora gestione esplicita. L’error handler va dopo le route e mantiene la firma a quattro parametri. Vedi Promise in Express 5.

Prova tu. Aggiungi log prima e dopo next e osserva l’ordine. Scrivi poi una 404 prima della route: vedrai perché quella route non viene più raggiunta.

Definizioni complete: dal termine al comportamento

Pipeline middleware
Un middleware riceve richiesta, risposta e next. Può arricchire il contesto, terminare la risposta o delegare. L’ordine è comportamento: il parser del body deve precedere chi legge req.body, un controllo di accesso deve precedere la risorsa protetta.
Delega e ritorno
next passa il controllo al middleware successivo, ma non equivale al return del linguaggio. Dopo next il codice della funzione può continuare. Scegli un solo esito per ramo: rispondere, delegare oppure propagare un errore; evita risposte duplicate e richieste lasciate aperte.
Middleware di errore
La firma (err, req, res, next) identifica il gestore di errore. Registralo dopo le route. In Express 5 le Promise restituite che falliscono sono propagate; callback asincrone esterne richiedono comunque gestione esplicita. Una route non trovata non diventa automaticamente un’eccezione.

API GET: elenco e dettaglio

Prima di iniziare: le parole della lezione

Risorsa e collezione
Una risorsa è un’entità esposta dall’API, per esempio una persona. Una collezione è un insieme di risorse.
Proiezione e contratto
Una proiezione sceglie quali campi restituire. Il contratto dell’API descrive URL, input, formato di risposta ed errori attesi.
RAM e persistenza
La RAM conserva i dati del processo in memoria. La persistenza li salva in modo da ritrovarli dopo un riavvio, per esempio in un database.

GET recupera risorse e non dovrebbe modificarle. Spesso un'API espone due route: elenco e dettaglio.

const persone = [{ id: 1, nome: 'Anna' }, { id: 2, nome: 'Luca' }];
app.get('/api/persone', (req, res) => res.json(persone));
app.get('/api/persone/:id', (req, res) => {
  const persona = persone.find(p => p.id === Number(req.params.id));
  if (!persona) return res.status(404).json({ errore: 'Non trovata' });
  res.json(persona);
});

Esempio aggiuntivo: GET /api/persone restituisce un array; GET /api/persone/1 un singolo oggetto. Gli esempi usano un array in memoria, quindi i dati scompaiono al riavvio.

Chi fa cosa, e perché

La GET dell’elenco restituisce più persone; quella del dettaglio ne cerca una. Una lista vuota è un risultato diverso da un singolo ID non trovato: nella prima situazione puoi rispondere 200 con [], nella seconda 404. La ricerca con find è lineare: su un array deve esaminare elementi fino a trovare quello giusto.

Importare persone.cjs non collega automaticamente una lettura al file sorgente a ogni richiesta. I dati caricati vivono nel processo: modificarli non riscrive il file JavaScript. Inoltre il contratto deve essere coerente: questa lezione restituisce un array nell’elenco, mentre il laboratorio aggiunge un oggetto con metadati totale e dati.

Un altro esempio guidato

// Frammento: app Express e array persone già definiti

  const dati = persone.map(({ id, nome }) => ({ id, nome }));
  res.json({ totale: dati.length, dati });
});

Come leggerlo e risultato atteso. map costruisce un nuovo array; il destructuring legge solo id e nome; l’oggetto finale espone quei campi. Se internamente aggiungi altri dati alla persona, questa risposta non li include automaticamente. Il totale qui è la lunghezza dell’elenco restituito.

Pratica attuale e precisazioni. Non esporre oggetti interni senza decidere i campi pubblici. In un sistema con database la query recupera i dati persistenti; il controller prepara la risposta. Una GET deve mantenere una semantica di lettura, anche se il server registra log o metriche.

Prova tu. Aggiungi un campo interno all’array e verifica che non compaia nella rubrica. Poi verifica elenco vuoto, ID valido e ID inesistente.

Collezione e dettaglio
GET /persone descrive una collezione e può restituire una lista vuota con 200. GET /persone/:id descrive un elemento: se non esiste, 404 comunica un risultato diverso dalla collezione vuota. Mantieni coerente la forma delle risposte per semplificare il client.

Una richiesta GET non dovrebbe creare o cancellare risorse come effetto richiesto. Browser, proxy e strumenti possono ripeterla o pre-caricarla. Log e metriche sono effetti collaterali operativi, diversi dalla modifica intenzionale dei dati di dominio.
Proiezione dei campi
Restituire un oggetto interno intero può esporre campi privati o dettagli del database. Costruisci esplicitamente la rappresentazione pubblica. Documenta filtri e ordinamento, e controlla i casi lista vuota, ID sconosciuto e input malformato.

API POST: creare risorse

Prima di iniziare: le parole della lezione

Creazione e validazione
Creare significa aggiungere una risorsa con una propria identità. Validare significa controllare i dati prima che modifichino lo stato.
Normalizzazione e whitelist
Normalizzare significa portare dati in una forma coerente, per esempio togliere spazi esterni. Una whitelist è l’elenco dei campi esplicitamente accettati.
Location
Header di risposta che può indicare l’URL della risorsa appena creata.

POST inserisce una nuova risorsa. I dati arrivano spesso nel body JSON, da validare prima dell'inserimento.

app.use(express.json());
let prossimoId = 3;
app.post('/api/persone', (req, res) => {
  const nome = req.body?.nome;
  if (typeof nome !== 'string' || !nome.trim()) {
    return res.status(400).json({ errore: 'Nome obbligatorio' });
  }
  const persona = { id: prossimoId++, nome: nome.trim() };
  persone.push(persona);
  res.status(201).json(persona);
});

Esempio aggiuntivo: due POST con lo stesso nome generano due record con ID distinti. In un'app reale occorrono regole di unicità e un database se sono richiesti.

Chi fa cosa, e perché

Il client invia il nome; il server controlla tipo e contenuto, assegna l’ID e aggiunge il record. Il client non deve scegliere l’ID per questa POST. trim() rimuove gli spazi iniziali e finali; va chiamato dopo aver verificato che il valore sia una stringa.

prossimoId++ usa il valore corrente e poi incrementa il contatore. È sufficiente per l’esempio con un singolo processo e dati in RAM. Non usare persone.length + 1: dopo una cancellazione potresti riutilizzare un ID già presente. In un sistema persistente la generazione degli ID va coordinata con l’archivio.

Un altro esempio guidato

// Frammento per l'API: persone e prossimoId già definiti
app.post('/api/iscritti', (req, res) => {
  const nome = req.body?.nome;
  if (typeof nome !== 'string' || nome.trim().length < 2) {
    return res.status(400).json({ errore: 'Nome di almeno 2 caratteri' });
  }
  const persona = { id: prossimoId++, nome: nome.trim() };
  persone.push(persona);
  return res.status(201).location(`/api/persone/${persona.id}`).json(persona);
});

Come leggerlo e risultato atteso. Il parser JSON deve essere registrato prima della route. ?. legge nome senza errore se il body manca. push modifica l’array; la risposta 201 restituisce la nuova persona. Location rimanda alla route di dettaglio già esistente per la stessa collezione.

Pratica attuale e precisazioni. Nel corso il successo viene talvolta restituito con 200: per questa creazione 201 comunica meglio il risultato. Costruisci il record con i campi ammessi invece di copiare indiscriminatamente tutto req.body. L’array rimane volatile e non viene scritto sul disco.

Prova tu. Invia un ID nel body e verifica che il server usi quello generato da lui. Invia poi due POST uguali: senza una regola di unicità o idempotenza creano due persone diverse.

Definizioni complete: dal termine al comportamento

Creazione e validazione
POST a una collezione può creare una nuova risorsa. Prima verifica forma del body, tipi, campi obbligatori e regole del dominio. Il parser JSON verifica soltanto la sintassi; non dimostra che nome sia una stringa non vuota o che età sia in un intervallo valido.
Identità e risposta
Assegna un ID stabile sul server o secondo un contratto esplicito. Una risposta 201 può includere la rappresentazione creata e un header Location con il suo indirizzo. L’ID non deve dipendere soltanto dalla lunghezza di un array che può ridursi.
Duplicati e retry
Se il client perde la risposta, non sa sempre se la creazione sia avvenuta. Ripetere POST può duplicare la risorsa. In contesti che lo richiedono, una chiave di idempotenza e una registrazione persistente dell’esito consentono di riconoscere lo stesso tentativo.

API PUT: aggiornare

Prima di iniziare: le parole della lezione

PUT e PATCH
PUT esprime la sostituzione della rappresentazione della risorsa all’URL indicato. PATCH esprime una modifica parziale descritta dal body.
Campi modificabili e identità
I campi modificabili costituiscono i dati che l’API permette al client di cambiare. L’identità della risorsa resta quella selezionata dall’URL.
Indice dell’array
Posizione numerica di un elemento, a partire da zero: non è l’ID dell’elemento e può cambiare dopo una cancellazione.

PUT serve convenzionalmente a sostituire la rappresentazione della risorsa; il corso lo usa per aggiornare un elemento di un array. Per modifiche parziali si usa spesso PATCH.

app.put('/api/persone/:id', (req, res) => {
  const id = Number(req.params.id);
  const persona = persone.find(p => p.id === id);
  if (!persona) return res.status(404).json({ errore: 'Non trovata' });
  const nome = req.body?.nome;
  if (typeof nome !== 'string' || !nome.trim())
    return res.status(400).json({ errore: 'Nome non valido' });
  persona.nome = nome.trim();
  res.json(persona);
});

Esempio aggiuntivo: con PUT /api/persone/2 e body {"nome":"Marco"}, l'oggetto con ID 2 viene aggiornato senza cambiare ID.

Chi fa cosa, e perché

Prima di aggiornare un elemento dell’array, cerca la persona per ID e valida tutti i dati da modificare. Non usare l’ID direttamente come indice: la persona 5 potrebbe trovarsi in posizione 2 oppure non esserci.

Nel modello ridotto con il solo campo nome, l’esempio PUT sopra sostituisce tutti i dati modificabili. Nel laboratorio i campi sono nome e ruolo: una PUT richiede entrambi. Se vuoi cambiare solo ruolo conservando nome, usa un contratto PATCH. Anche una PATCH può essere idempotente quando assegna valori, ma non lo è necessariamente quando esprime operazioni come “incrementa”.

Un altro esempio guidato

// Frammento: aggiunta all'API persone con campo ruolo
app.patch('/api/persone/:id', (req, res) => {
  const id = Number(req.params.id);
  if (!Number.isSafeInteger(id) || id <= 0)
    return res.status(400).json({ errore: 'ID non valido' });
  const persona = persone.find(p => p.id === id);
  if (!persona) return res.status(404).json({ errore: 'Non trovata' });
  const ruolo = req.body?.ruolo;
  if (typeof ruolo !== 'string' || !ruolo.trim() || ruolo.trim().length > 80)
    return res.status(400).json({ errore: 'Ruolo non valido' });
  persona.ruolo = ruolo.trim();
  res.json(persona);
});

Come leggerlo e risultato atteso. Inviando {"ruolo":"editor"} modifichi il ruolo senza toccare nome e ID. Questa PATCH accetta il solo campo ruolo come modifica; un body senza ruolo non è valido. È una scelta del contratto, non un formato universale per tutte le PATCH.

Pratica attuale e precisazioni. Una PUT può anche creare una risorsa secondo il contratto dell’API; qui restituiamo 404 se manca. Non obbligare il client a rispedire un ID nel body e non permettere che un ID diverso sovrascriva quello selezionato dal percorso.

Prova tu. Invia la stessa PUT due volte: lo stato finale deve restare uguale. Confronta poi una PUT senza ruolo nel laboratorio con la PATCH qui sopra.

Definizioni complete: dal termine al comportamento

Sostituzione e modifica parziale
PUT esprime lo stato desiderato completo della risorsa secondo il contratto; PATCH esprime una modifica parziale. Se chiami PUT un aggiornamento parziale senza documentarlo, il client non sa se i campi omessi restano o vengono rimossi. Decidi e testa questa semantica.
Aggiornamento e identità
L’ID nel percorso identifica l’oggetto da aggiornare e non dovrebbe cambiare perché il body ne propone un altro. Valida la rappresentazione prima di modificare lo stato. Un fallimento di validazione non deve lasciare metà dei campi già aggiornati.
Conflitti concorrenti
Due client possono leggere la stessa versione e poi sovrascriversi. Un controllo di versione o un ETag con If-Match consente di rifiutare aggiornamenti basati su uno stato vecchio. L’idempotenza di PUT non risolve da sola la concorrenza.

API DELETE: eliminare

Prima di iniziare: le parole della lezione

findIndex e splice
findIndex trova la posizione di un elemento e restituisce -1 se manca. splice modifica l’array eliminando o inserendo elementi a partire da una posizione.
204 No Content
Risposta di successo senza body. Il client non deve tentare di leggerla come JSON.
Cancellazione logica
Alternativa alla rimozione fisica: si marca un record come eliminato e lo si esclude dalle normali letture, secondo le regole applicative.

DELETE rimuove una risorsa individuata normalmente da un ID. Evita di confondere l'ID pubblico con l'indice dell'array: possono essere diversi.

app.delete('/api/persone/:id', (req, res) => {
  const id = Number(req.params.id);
  const posizione = persone.findIndex(p => p.id === id);
  if (posizione === -1)
    return res.status(404).json({ errore: 'Non trovata' });
  persone.splice(posizione, 1);
  res.status(204).end();
});

Esempio aggiuntivo: dopo aver eliminato l'ID 1, gli altri ID non dovrebbero essere ricalcolati. 204 non ha body; 200 con una conferma JSON è un'alternativa.

Chi fa cosa, e perché

findIndex collega l’ID pubblico alla posizione corrente nell’array. Verifica sempre -1: chiamare splice(-1, 1) elimina l’ultimo elemento, anche se quello richiesto non esiste. Dopo la rimozione non ricalcolare gli ID dei sopravvissuti: i loro URL devono continuare a identificare le stesse persone.

Una seconda DELETE può ricevere 404 dopo che la prima ha ricevuto 204. Questo non contraddice l’idempotenza: in entrambi i casi lo stato finale desiderato è che la risorsa non esista. Alcune API scelgono 204 anche se il record è già assente: documenta la politica.

Un altro esempio guidato

});

} else {
  console.log('Status:', risposta.status, 'Risposta:', await risposta.text());
}

Come leggerlo e risultato atteso. Alla prima esecuzione ottieni normalmente 204. La seconda restituisce 404 e il messaggio dell’API, se il server non è stato riavviato. response.json() su una risposta 204 fallirebbe perché non c’è testo JSON da interpretare.

Pratica attuale e precisazioni. La rimozione in RAM non equivale a una cancellazione persistente. In sistemi reali vanno definite anche dipendenze fra record, permessi e possibilità di recupero; la cancellazione logica è una scelta di modello, non una proprietà automatica del metodo DELETE.

Prova tu. Elimina un ID intermedio e recupera gli altri. Verifica che un ID inesistente non causi la cancellazione accidentale dell’ultimo elemento.

Definizioni complete: dal termine al comportamento

Cancellazione e risposta
DELETE richiede di rimuovere l’associazione della risorsa al suo indirizzo secondo le regole dell’applicazione. Una risposta 204 comunica successo senza body: non inviare JSON insieme a quel codice. Puoi usare 200 quando vuoi restituire una rappresentazione dell’esito.
Ripetizione della richiesta
Dopo una prima eliminazione, una seconda può ricevere 404 oppure un successo documentato. Le risposte possono differire pur restando idempotente l’effetto desiderato: la risorsa è assente. I test devono controllare lo stato finale, non solo l’uguaglianza degli status.
Integrità e autorizzazione
Una risorsa può essere referenziata da altre: stabilisci se impedire, propagare o rendere logica la cancellazione. Controlla chi può cancellare prima di mutare i dati. Sapere un ID non concede automaticamente il diritto di eliminare quella risorsa.

Express Router e organizzazione

Prima di iniziare: le parole della lezione

Router e prefisso
Un Router è un insieme componibile di route e middleware. Il prefisso di montaggio collega quel gruppo a una parte dell’URL dell’app.
Controller, service e repository
Il controller gestisce ingresso e risposta HTTP; il service applica regole del dominio; il repository legge e scrive i dati. Sono ruoli organizzativi, non oggetti creati automaticamente da Express.
MVC
Model–View–Controller: separa modello e dati, presentazione e gestione dell’interazione. In un’API JSON la presentazione non è necessariamente una pagina HTML.

Con l'aumentare delle route conviene separarle dal file principale. express.Router() consente di raggruppare endpoint e middleware.

// routes/persone.cjs
const express = require('express');
const router = express.Router();
router.get('/', (req, res) => res.json([{ id: 1, nome: 'Anna' }]));
router.get('/:id', (req, res) => res.json({ id: Number(req.params.id) }));
module.exports = router;

// server.cjs
const express = require('express');
const personeRouter = require('./routes/persone.cjs');
const app = express();
app.use('/api/persone', personeRouter);
app.listen(3000);

Esempio aggiuntivo: un futuro progetto può dividere codice in routes/, controllers/, services/ e repositories/. MVC e database sono possibili approfondimenti successivi.

Chi fa cosa, e perché

app.use("/api/persone", personeRouter) affida al router le richieste sotto quel prefisso. All’interno scrivi router.get("/") e router.get("/:id"). Ripetere /api/persone dentro il router produrrebbe un percorso duplicato. Per una richiesta al router, req.originalUrl conserva l’URL originale, mentre Express gestisce il percorso relativo al montaggio.

La catena completa può essere: server → parser e middleware → router → controller → service → repository → risposta. Il router sceglie chi gestisce la richiesta; non è lui, da solo, a rendere persistenti i dati. Parti da pochi file con responsabilità chiare e separali quando questo rende il flusso più comprensibile.

Un altro esempio guidato

Promise, async/await e concorrenza controllata

Prerequisiti: lezioni 05, 07 e 12. Impara a distinguere un valore futuro dal lavoro che lo produce.

Definizioni

Promise
Un oggetto che rappresenta il futuro esito di un’operazione: pending mentre non è conclusa, fulfilled con un valore oppure rejected con un motivo. Una volta conclusa non cambia esito. Una Promise non è di per sé un thread e non rende ogni operazione non bloccante.
async e await
Una funzione async restituisce sempre una Promise. await sospende la continuazione di quella funzione fino all’esito, senza sospendere tutto il processo. Il codice sincrono prima e dopo l’attesa continua a usare il thread JavaScript.
Composizione e fallimento
Promise.all raccoglie i risultati nell’ordine degli input e fallisce al primo rifiuto osservato, ma non annulla automaticamente le altre operazioni. Promise.allSettled permette di ispezionare anche esiti parziali.

Esperimento riproducibile

Salva come concorrenza.mjs ed esegui node concorrenza.mjs. Non richiede pacchetti esterni.

import { setTimeout as pausa } from 'node:timers/promises';
async function lavoro(nome, durata) {
  await pausa(durata);
  return nome;
}
console.time('sequenza');
const a = await lavoro('A', 100);
const b = await lavoro('B', 100);
console.timeEnd('sequenza');
console.time('insieme');
const risultati = await Promise.all([
  lavoro('A', 100), lavoro('B', 100)
]);
console.timeEnd('insieme');
console.log(a, b, risultati);

Che cosa osservare

La sequenza impiega circa 200 ms; le attese avviate insieme circa 100 ms, con variazioni dovute al sistema. L’array finale mantiene A prima di B anche se cambi le durate. Non hai accelerato un calcolo: hai sovrapposto due attese indipendenti.

Errori e limiti

Metti try/catch intorno a un await quando puoi recuperare o aggiungere contesto. Una chiamata async non attesa può fallire dopo che il chiamante ha già terminato. Non avviare migliaia di richieste senza limite: memoria, connessioni e servizio remoto hanno capacità finite. Elabora piccoli gruppi o usa una coda di lavoro.

Prova tu

Fai fallire B e confronta all con allSettled. Poi aggiungi C e avvia al massimo due lavori per volta.

Criteri di verifica

Con all entra nel catch; A può continuare comunque. Con allSettled ottieni un risultato per ciascun input, con status fulfilled o rejected. Nei gruppi di due, C deve partire soltanto dopo il primo gruppo.

Validazione e gestione degli errori

Prerequisiti: lezioni 19–22 e 25. Definisci un contratto verificabile anche quando il client sbaglia.

Dal formato al significato

Parsing
Trasforma il testo JSON in valori JavaScript; può fallire prima della route se il testo è malformato.
Validazione
Verifica forma, tipi, intervalli e regole del dato. La stringa vuota e un array sono JSON validi ma possono essere input non ammessi.
Normalizzazione
Converte input accettati in una forma uniforme, come un nome senza spazi esterni. Va documentata: non deve nascondere errori o trasformare qualunque valore in una stringa.
Errore atteso e inatteso
Un errore atteso, come un campo assente, può essere spiegato al client. Un errore inatteso richiede un log interno e una risposta che non esponga stack, credenziali o dettagli del filesystem.

Una funzione indipendente da Express

Salva come persona.mjs. È riutilizzata nella prossima lezione.

export function validaPersona(body) {
  if (!body || typeof body !== 'object' || Array.isArray(body)) {
    return { ok: false, error: 'È richiesto un oggetto' };
  }
  if (typeof body.nome !== 'string' ||
      body.nome.trim().length === 0 || body.nome.trim().length > 80) {
    return { ok: false, error: 'nome: da 1 a 80 caratteri' };
  }
  if (!Number.isInteger(body.eta) || body.eta < 0 || body.eta > 130) {
    return { ok: false, error: 'eta: intero da 0 a 130' };
  }
  return { ok: true, value: { nome: body.nome.trim(), eta: body.eta } };
}

La funzione non modifica il body e seleziona esplicitamente i campi ammessi. eta: "18" viene rifiutato: il contratto richiede un numero JSON. La lunghezza delle stringhe JavaScript misura unità UTF-16, non sempre caratteri percepiti dall’utente; chiarisci il requisito se gestisci nomi internazionali.

Che cosa stai verificando

Test unitario
Controlla una responsabilità piccola in isolamento, come la validazione di un body. È veloce e individua bene quale regola è stata violata.
Test di integrazione
Verifica la collaborazione tra componenti: parser, route, servizio e archivio. Può individuare un ordine errato dei middleware che un test della sola funzione non vedrebbe.
Asserzione e regressione
Un’asserzione confronta il comportamento con una proprietà attesa e fallisce se non coincide. Una regressione è un comportamento corretto che si rompe dopo una modifica; un test conservato ne rende visibile il ritorno.
Fixture e isolamento
Una fixture prepara dati iniziali noti. Un test isolato non dipende dall’ordine di esecuzione né dai dati lasciati da un altro test.

LEZIONE 32 · Affidabilità

Persistenza, concorrenza e limiti del file JSON

Prerequisiti: lezioni 07, 19 e 29. Comprendi cosa significa conservare dati oltre la vita del processo.

Definizioni e scelte

Memoria volatile e persistenza
Una variabile vive nel processo; un file può essere letto dopo il riavvio. Persistenza non significa automaticamente backup, disponibilità o integrità: un file può essere sovrascritto, corrotto o perso.
Read-modify-write
È la sequenza leggi, modifica e riscrivi. Tra lettura e scrittura un altro attore può modificare gli stessi dati. L’ultima scrittura può cancellare l’effetto della precedente, anche se entrambe le richieste ricevono successo.
Transazione
Raggruppa operazioni con garanzie definite di atomicità e isolamento. Un database può offrire strumenti per gestire aggiornamenti concorrenti; leggere e riscrivere JSON non crea una transazione.

Archivio minimo per un processo CLI

Salva come archivio.mjs. Usa un file dedicato al laboratorio; questo esempio è per esecuzioni sequenziali e non va usato come archivio concorrente di un server.

import { readFile, writeFile } from 'node:fs/promises';
const file = new URL('./persone-lab.json', import.meta.url);
async function carica() {
  let testo;
  try { testo = await readFile(file, 'utf8'); }
  catch (err) {
    if (err.code === 'ENOENT') return [];
    throw err;
  }
  const dati = JSON.parse(testo);
  if (!Array.isArray(dati) || !dati.every(p =>
      p && typeof p.nome === 'string')) {
    throw new Error('Archivio non valido');
  }
  return dati;
}
const persone = await carica();
persone.push({ nome: 'Ada' });
await writeFile(file, JSON.stringify(persone, null, 2), 'utf8');
console.log('Persone salvate:', persone.length);

Verifica guidata

  1. Su una cartella nuova esegui node archivio.mjs: stampa 1 e crea il file.
  2. Eseguilo nuovamente: stampa 2. Il dato è sopravvissuto al primo processo.
  3. In una copia di prova rendi il JSON invalido: l’esecuzione deve fallire senza sostituirlo con una lista vuota.

Perché non basta per un server

La scrittura diretta può lasciare un file parziale in caso di interruzione. Scrivere un file temporaneo e rinominarlo può ridurre alcuni rischi, ma non risolve aggiornamenti persi, accesso multiprocesso o tutte le garanzie di durabilità. Una coda interna serializza soltanto chi passa per quella stessa coda; un secondo processo la ignora.

Spiegazione

2. Server completo (un solo file)

const express = require('express');
const app = express();
const PORT = 3000;

let persone = [
  { id: 1, nome: 'Anna', ruolo: 'designer' },
  { id: 2, nome: 'Luca', ruolo: 'developer' }
];
let prossimoId = 3;

// Middleware: registra metodo, percorso e tempo impiegato.
app.use((req, res, next) => {
  const inizio = Date.now();
  res.on('finish', () => {
    console.log(req.method, req.originalUrl, res.statusCode,
      `${Date.now() - inizio}ms`);
  });
  next();
});

// Il parser viene dopo il logger e prima delle route.
app.use(express.json({ limit: '32kb' }));

function nomeValido(nome) {
  return typeof nome === 'string' &&
    nome.trim().length >= 2 && nome.trim().length <= 80;
}
function idRichiesto(req, res) {
  const testo = req.params.id;
  const id = Number(testo);
  if (!/^[1-9]\d*$/.test(testo) || !Number.isSafeInteger(id)) {
    res.status(400).json({ errore: 'ID non valido' });
    return null;
  }
  return id;
}

// GET /api/persone?cerca=an&limite=10
app.get('/api/persone', (req, res) => {
  const { cerca = '', limite: testoLimite = '20' } = req.query;
  if (typeof cerca !== 'string' || typeof testoLimite !== 'string' ||
      !/^[1-9]\d*$/.test(testoLimite)) {
    return res.status(400).json({ errore: 'Query non valida' });
  }
  const limite = Number(testoLimite);
  if (!Number.isSafeInteger(limite) || limite > 100)
    return res.status(400).json({ errore: 'Limite da 1 a 100' });
  const risultati = persone.filter(p =>
    p.nome.toLowerCase().includes(cerca.toLowerCase())
  ).slice(0, limite);
  res.json({ totale: risultati.length, dati: risultati });
});

// GET /api/persone/:id
app.get('/api/persone/:id', (req, res) => {
  const id = idRichiesto(req, res);
  if (id === null) return;
  const persona = persone.find(p => p.id === id);
  if (!persona) return res.status(404).json({ errore: 'Non trovata' });
  res.json(persona);
});

// POST /api/persone
app.post('/api/persone', (req, res) => {
  const { nome, ruolo = 'utente' } = req.body ?? {};
  if (!nomeValido(nome) || typeof ruolo !== 'string' || !ruolo.trim() || ruolo.trim().length > 80)
    return res.status(400).json({ errore: 'Dati non validi' });
  const persona = { id: prossimoId++, nome: nome.trim(), ruolo: ruolo.trim() };
  persone.push(persona);
  res.status(201).location(`/api/persone/${persona.id}`).json(persona);
});

// PUT /api/persone/:id
app.put('/api/persone/:id', (req, res) => {
  const id = idRichiesto(req, res);
  if (id === null) return;
  const persona = persone.find(p => p.id === id);
  if (!persona) return res.status(404).json({ errore: 'Non trovata' });
  const { nome, ruolo } = req.body ?? {};
  if (!nomeValido(nome) || typeof ruolo !== 'string' || !ruolo.trim() || ruolo.trim().length > 80)
    return res.status(400).json({ errore: 'Dati non validi' });
  persona.nome = nome.trim();
  persona.ruolo = ruolo.trim();
  res.json(persona);
});

// PATCH /api/persone/:id — modifica soltanto il ruolo
app.patch('/api/persone/:id', (req, res) => {
  const id = idRichiesto(req, res);
  if (id === null) return;
  const persona = persone.find(p => p.id === id);
  if (!persona) return res.status(404).json({ errore: 'Non trovata' });
  const ruolo = req.body?.ruolo;
  if (typeof ruolo !== 'string' || !ruolo.trim() || ruolo.trim().length > 80)
    return res.status(400).json({ errore: 'Ruolo non valido' });
  persona.ruolo = ruolo.trim();
  res.json(persona);
});

// DELETE /api/persone/:id
app.delete('/api/persone/:id', (req, res) => {
  const id = idRichiesto(req, res);
  if (id === null) return;
  const prima = persone.length;
  persone = persone.filter(p => p.id !== id);
  if (persone.length === prima)
    return res.status(404).json({ errore: 'Non trovata' });
  res.status(204).end();
});

app.use((req, res) => res.status(404).json({ errore: 'Endpoint non trovato' }));
app.use((err, req, res, next) => {
  if (res.headersSent) return next(err);
  if (err.type === 'entity.parse.failed')
    return res.status(400).json({ errore: 'JSON malformato' });
  if (err.type === 'entity.too.large')
    return res.status(413).json({ errore: 'Body oltre 32kb' });
  if (Number.isInteger(err.status) && err.status >= 400 && err.status < 500)
    return res.status(err.status).json({ errore: 'Richiesta non valida' });
  console.error(err);
  res.status(500).json({ errore: 'Errore interno' });
});
app.listen(PORT, '127.0.0.1', () => console.log(`API: http://localhost:${PORT}`));

5. Il viaggio di una richiesta, passo per passo

Client→ Logger→ Parser JSON→ Route→ Validazione→ Array in RAM→ Risposta

Per una POST, il client invia un testo JSON. Il logger registra una funzione sull’evento finish della risposta, poi chiama next. Il parser interpreta il testo. La route legge i campi ammessi, li valida e costruisce una nuova persona; push aggiorna l’array. Infine status, Location e json preparano e inviano la risposta. A quel punto il listener finish registra status e durata: questa misura la conclusione dell’invio dal server, non dimostra che l’utente abbia già letto il contenuto.

ParteResponsabilitàCosa controllare

totale è qui il numero di risultati restituiti dopo il limite, non il numero di tutte le corrispondenze possibili. Non sono implementati offset o cursori di paginazione. res.headersSent indica che gli header sono già partiti: in quel caso il gestore passa l’errore alla gestione successiva, evitando una seconda risposta. Per approfondire: gestione errori Express e errori dei parser.

Controlli negativi con risultati attesi

  • GET /api/persone/abc → 400; GET /api/persone/999 → 404.
  • GET /api/persone?limite=0 o ?limite=2&limite=3 → 400.
  • POST con {"nome":" "} → 400 e nessun inserimento.
  • POST con JSON troncato, per esempio {"nome": → 400, non 500.
  • PUT senza ruolo → 400; PATCH con ruolo valido → 200 senza cambiare nome.
  • DELETE ripetuta sullo stesso ID → prima 204, poi 404.
  • Riavvio del server → dati iniziali ripristinati: l’array non è persistente.

Il contatore e l’array sono condivisi soltanto nel singolo processo. Per dati durevoli e più istanze serve un archivio coordinato. Gli esempi non implementano utenti autenticati: il campo ruolo è un semplice dato descrittivo della persona e non conferisce permessi all’applicazione.

Domande di ripasso con risposta

Chi esegue il codice della route?
Node esegue la funzione JavaScript che Express ha selezionato in base a metodo, percorso e ordine dei middleware.
Perché req.body può essere assente?
Il parser può mancare, essere registrato troppo tardi, non riconoscere il Content-Type o non avere un body da interpretare.
Perché una POST scompare dopo un salvataggio?
Se il watcher riavvia il processo, l’array in RAM viene ricreato. La persistenza richiede un salvataggio esplicito.
Un await rende il calcolo parallelo?
No: permette di attendere una Promise senza bloccare la funzione chiamante nello stesso modo di una chiamata sincrona, ma un calcolo pesante sul thread principale resta bloccante.
Qual è la differenza fra 400 e 404?
400 descrive input non valido; 404 una risorsa o route non trovata, secondo il contratto dell’API.
