HTTP, pagine e immagini

Come lavoriamo

Servono Node.js, un editor e un terminale. Le prime tappe richiedono soltanto variabili, funzioni e if. Procedi una tappa alla volta: la successiva ha senso quando sai spiegare e riprodurre il risultato della precedente.

  1. Crea una cartella lab-http e aprila nel terminale.
  2. Crea server.cjs: l’estensione permette di usare require.
  3. Copia il blocco completo della tappa, poi esegui node server.cjs.
  4. Apri l’indirizzo stampato nel terminale.

A ogni nuova versione: ferma Node con Ctrl+C, sostituisci tutto server.cjs, salva e riavvia. Non incollare un server sotto l’altro. Per provare i comandi usa un secondo terminale mentre il primo tiene acceso Node. Su Windows usa curl.exe; su macOS/Linux usa curl.

IP è l’indirizzo su cui il server ascolta; 127.0.0.1 indica questo computer. PORT è la porta scelta per il laboratorio. Usiamo entrambi in listen(PORT, IP, ...) e nel messaggio di avvio, così l’indirizzo stampato corrisponde alla configurazione.

Non servono pacchetti esterni nei primi due laboratori. Puoi distribuire queste tappe su più incontri: non sono una corsa da completare in un’unica ora.

TAPPA 1

Un server che risponde a tutto

Obiettivo: inviare una prima risposta. createServer riceve una funzione che Node esegue a ogni richiesta: req descrive ciò che arriva, res permette di rispondere. Per ora non controlliamo metodo e URL.

server.cjs · versione 1

const http = require('node:http');

const IP = '127.0.0.1';
const PORT = 3000;

const server = http.createServer((req, res) => {
  res.writeHead(200, { 'Content-Type': 'text/plain; charset=utf-8' });
  res.end('Ciao! Il server risponde.');
});

server.listen(PORT, IP, () => {
  console.log('Server attivo su http://' + IP + ':' + PORT);
});

writeHead imposta lo stato e gli header. text/plain dice “testo semplice”; charset=utf-8 permette di interpretare anche gli accenti. end invia il contenuto e conclude la risposta.

Prova nel secondo terminale

curl.exe -i http://127.0.0.1:3000/
curl.exe -i http://127.0.0.1:3000/qualsiasi
curl.exe -i -X POST http://127.0.0.1:3000/prova

Risultato atteso. Tutte e tre le richieste restituiscono 200 e “Ciao! Il server risponde.”. Il browser mostra lo stesso saluto su qualsiasi percorso. HEAD è un caso particolare del protocollo: riceve gli header senza il corpo.

Tocca a te. Modifica il saluto. Poi cambia PORT in 3001: riavvia e controlla che anche il messaggio stampato contenga 3001. Ripristina 3000 per le prossime prove. Avvia una richiesta e indica quale parte riguarda req e quale res.

TAPPA 2

Accettare soltanto GET

Aggiungiamo una sola regola: controlliamo req.method. Scrivere un indirizzo nel browser invia normalmente GET. Per provare POST usiamo il terminale.

server.cjs · versione 2

const http = require('node:http');

const IP = '127.0.0.1';
const PORT = 3000;

const server = http.createServer((req, res) => {
  if (req.method !== 'GET') {
    res.writeHead(405, { 'Content-Type': 'text/plain; charset=utf-8', 'Allow': 'GET' });
    res.end('Metodo non consentito. Usa GET.');
    return;
  }

  res.writeHead(200, { 'Content-Type': 'text/plain; charset=utf-8' });
  res.end('Hai usato GET.');
});

server.listen(PORT, IP, () => {
  console.log('Server attivo su http://' + IP + ':' + PORT);
});

Se il metodo non è GET rispondiamo con 405. L’header Allow: GET indica il metodo accettato. Il return termina questa esecuzione della funzione: senza di esso proseguiremmo tentando di rispondere una seconda volta.

Prova nel secondo terminale

curl.exe -i http://127.0.0.1:3000/qualsiasi
curl.exe -i -X POST http://127.0.0.1:3000/

Risultato atteso. GET restituisce 200 anche su /qualsiasi; POST restituisce 405. Non abbiamo ancora limitato il percorso.

Tocca a te. Prova PUT e DELETE al posto di POST: devono essere rifiutati. Prima di cambiare codice, spiega perché GET /qualsiasi è ancora accettato.

TAPPA 3

GET e URL insieme: soltanto la home HTML

Ora aggiungiamo il percorso. La condizione req.method === 'GET' && req.url === '/' significa: il metodo deve essere GET e l’URL deve essere esattamente /. Solo questa combinazione riceve la home.

server.cjs · versione 3

const http = require('node:http');

const IP = '127.0.0.1';
const PORT = 3000;

const server = http.createServer((req, res) => {
  // && significa: devono essere vere entrambe le condizioni.
  if (req.method === 'GET' && req.url === '/') {
    res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' });
    res.end('<h1>Ciao da Node.js!</h1><p>Questa risposta contiene HTML.</p>');
    return;
  }

  if (req.method !== 'GET') {
    res.writeHead(405, { 'Content-Type': 'text/plain; charset=utf-8', 'Allow': 'GET' });
    res.end('Metodo non consentito. Usa GET.');
    return;
  }

  res.writeHead(404, { 'Content-Type': 'text/plain; charset=utf-8' });
  res.end('Pagina non trovata.');
});

server.listen(PORT, IP, () => {
  console.log('Server attivo su http://' + IP + ':' + PORT);
});

Il corpo è ora una stringa HTML e il tipo è text/html: il browser interpreta h1 e p. Non leggiamo ancora un file dal disco. Il confronto dell’URL è esatto: anche /?nome=Ada per ora non coincide con /.

Prova nel secondo terminale

curl.exe -i http://127.0.0.1:3000/
curl.exe -i http://127.0.0.1:3000/altra
curl.exe -i -X POST http://127.0.0.1:3000/

Risultato atteso. GET / → 200 HTML; GET /altra → 404; POST / → 405. Apri la home nel browser: vedi il titolo formattato, non i tag scritti come testo.

Tocca a te. Cambia il testo dell’h1. Poi prova a chiedere /home: prevedi la risposta e spiega quale confronto fallisce.

TAPPA 4 · PAUSA DI COMPRENSIONE

Fermiamoci sugli status code HTTP

Questa tappa non aggiunge una versione di server.cjs. Mantieni la versione 3 e impara a leggere la risposta. Uno status è un numero nella prima riga HTTP: non dipende dalle parole scritte nel corpo. Scrivere “Errore” con stato 200 resta una risposta 200.

CodiceSignificato quiQuando lo incontriamo
200 OKRichiesta completataLa home esiste
201 CreatedRisorsa creataPiù avanti: POST crea una nota
204 No ContentOperazione riuscita, senza corpoPiù avanti: cancellazione
400 Bad RequestDati della richiesta non validiPiù avanti: un campo vuoto
404 Not FoundRisorsa o percorso non trovatoGET /altra
405 Method Not AllowedMetodo non ammesso per quella risorsaPOST sulla home; aggiungiamo Allow
409 ConflictOperazione in conflitto con lo stato attualePiù avanti: seconda creazione della stessa nota
415 Unsupported Media TypeFormato del corpo non supportatoPiù avanti: JSON dove aspettiamo testo

Le famiglie aiutano a orientarsi: 2xx successo, 3xx reindirizzamento, 4xx richiesta non soddisfatta per un problema lato client, 5xx errore lato server. Studiamo 200, 404 e 405 adesso; riprenderemo gli altri quando servono.

Prova nel secondo terminale

curl.exe -i http://127.0.0.1:3000/
curl.exe -i http://127.0.0.1:3000/altra
curl.exe -i -X POST http://127.0.0.1:3000/

Risultato atteso. Leggi la prima riga, poi Content-Type, poi il corpo separato dagli header da una riga vuota. Nel browser puoi vedere gli stessi dati nella scheda Rete/Network.

Tocca a te. Annota prima di eseguire i comandi: metodo, URL, status atteso e motivo. Cambia temporaneamente il 404 nel codice in 200 lasciando il testo uguale: verifica che il testo non determini lo status, poi ripristina 404.

TAPPA 5

Tre rotte: HTML, JSON e testo

Solo ora allarghiamo il server. La home resta HTML; /info restituisce un oggetto trasformato in JSON; /saluto restituisce testo. Continuiamo con confronti diretti su req.url, senza introdurre ancora un analizzatore di URL.

server.cjs · versione 4

const http = require('node:http');

const IP = '127.0.0.1';
const PORT = 3000;

const server = http.createServer((req, res) => {
  if (req.method !== 'GET') {
    res.writeHead(405, { 'Content-Type': 'text/plain; charset=utf-8', 'Allow': 'GET' });
    res.end('Metodo non consentito. Usa GET.');
    return;
  }

  if (req.url === '/') {
    res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' });
    res.end('<h1>Home</h1><p>Benvenuto nel laboratorio.</p>');
    return;
  }

  if (req.url === '/info') {
    res.writeHead(200, { 'Content-Type': 'application/json; charset=utf-8' });
    res.end(JSON.stringify({ corso: 'Node.js', aula: 3 }));
    return;
  }

  if (req.url === '/saluto') {
    res.writeHead(200, { 'Content-Type': 'text/plain; charset=utf-8' });
    res.end('Ciao dalla rotta /saluto!');
    return;
  }

  res.writeHead(404, { 'Content-Type': 'text/plain; charset=utf-8' });
  res.end('Pagina non trovata.');
});

server.listen(PORT, IP, () => {
  console.log(`Server attivo su http://${IP}:${PORT}`);
});

JSON.stringify converte l’oggetto JavaScript in una stringa JSON da inviare. Il Content-Type descrive ciò che stiamo realmente spedendo.

Nel messaggio di avvio compaiono per la prima volta i backtick: `http://${IP}:${PORT}` inserisce i valori dentro la stringa. È un altro modo di scrivere la concatenazione delle prime versioni; la funzione di listen non cambia. I backtick sono il carattere `, diverso dall’apostrofo.

Prova nel secondo terminale

curl.exe -i http://127.0.0.1:3000/
curl.exe -i http://127.0.0.1:3000/info
curl.exe -i http://127.0.0.1:3000/saluto
curl.exe -i http://127.0.0.1:3000/inesistente

Risultato atteso. Nell’ordine: 200 text/html, 200 application/json, 200 text/plain, 404. /info?classe=4A dà ancora 404, perché il confronto è esatto.

Tocca a te. Aggiungi GET /classe con un oggetto JSON che contenga nome e aula, prima della 404. Ripeti la prova e controlla anche Content-Type.

TAPPA 6

HTML incorporato: navigare con i link

Costruiamo la prima piccola interfaccia. L’HTML è ancora scritto dentro server.cjs. I backtick permettono anche una stringa su più righe. La nuova pagina ha due link; /contatti è un’altra pagina HTML con il ritorno alla home.

Apri http://127.0.0.1:3000/ e segui i link. Ogni clic fa una nuova richiesta GET e il browser mostra la risposta al posto della pagina precedente. Non c’è JavaScript nel frontend.

Anche un URL completo come http://127.0.0.1:3000/saluto funziona, ma il percorso con / continua a funzionare se cambiamo PORT. Qui facciamo navigazione di pagine; un’API dati è pensata per un programma che legge una risposta, come il JSON della tappa precedente. Tutte queste richieste usano comunque HTTP.

Risultato atteso. Il link al saluto mostra testo; il link ai contatti apre una seconda pagina HTML; “Torna alla home” riapre /. Nessun fetch, nessun async/await.

Tocca a te. Aggiungi un link /orari e una rotta che restituisce una pagina con l’orario del laboratorio e un link per tornare indietro.

TAPPA 7

HTML incorporato: un pulsante GET

Facciamo un secondo esempio minimale. Un pulsante dentro un form GET può chiedere un’altra rotta senza script. Il form non ha campi: serve soltanto per navigare.

server.cjs · versione 6

const http = require('node:http');

const IP = '127.0.0.1';
const PORT = 3000;

const server = http.createServer((req, res) => {
  if (req.method !== 'GET') {

});

Un form GET può costruire un URL con parametri: pathname riconosce il percorso indipendentemente dalla query. Prima di passare ai file, fermiamoci a capire dove viaggiano questi dati.

Prova nel secondo terminale

curl.exe -i "http://127.0.0.1:3000/saluto?nome=Ada"

Risultato atteso. Il pulsante apre /saluto e mostra il testo. Anche la richiesta con ?nome=Ada funziona: stiamo ignorando i parametri, non li stiamo ancora usando.

Tocca a te. Aggiungi un secondo form GET con un pulsante che apre /contatti. Osserva metodo e URL in Network. Spiega perché questo clic naviga, invece di cambiare una parte della pagina.

Una GET può trasmettere dati senza un body

Nelle richieste GET di questo laboratorio non inviamo un corpo. Possiamo comunque mandare informazioni al server scrivendole nell’URL. Per esempio, chiediamo un saluto per una certa persona e una certa classe:

http://127.0.0.1:3000/saluto?nome=Ada&classe=4A

Il percorso /saluto sceglie la rotta. La parte nome=Ada&classe=4A, chiamata query string, fornisce due parametri per quella richiesta. I nomi nome e classe sono una scelta del nostro programma: il server deve leggerli e decidere come usarli. Il punto interrogativo da solo non esegue alcuna ricerca.

Tre caratteri da imparare per primi: ?, = e &

CarattereFunzione nella query di questo esempioEsempio
?Segna l’inizio della query, dopo il percorso./saluto?nome=Ada
=Separa il nome del parametro dal suo valore.nome=Ada
&Separa una coppia nome=valore dalla successiva.nome=Ada&classe=4A

La lettura è: «Richiedo /saluto, passando nome uguale ad Ada e classe uguale a 4A». Dopo il primo parametro aggiungiamo gli altri con &, non con un altro ?. Nella convenzione dei parametri non stiamo facendo un’operazione matematica o una condizione JavaScript: separiamo nomi e valori.

Come parte quella richiesta? Anche senza form

Puoi scrivere l’indirizzo completo nella barra del browser oppure seguire un normale link. Il server riceve gli stessi parametri. In un attributo HTML scriviamo il separatore & come &amp;; il browser lo interpreta come un normale & nell’URL:

<a href="/saluto?nome=Ada&amp;classe=4A">Saluta Ada della 4A</a>

Il form GET è un terzo modo: il browser costruisce la query usando il name e il valore di ciascun campo. Un campo senza name non viene incluso come parametro. Il nome del parametro non viene preso dall’etichetta visibile né dall’attributo id.

In una rappresentazione HTTP/1.1 semplificata, la richiesta è questa. I dati sono già nella prima riga; non c’è un body contenente nome e classe:

GET /saluto?nome=Ada&classe=4A HTTP/1.1
Host: 127.0.0.1:3000

GET significa chiedere una risorsa; i parametri possono specificare filtri, pagina dei risultati o un identificatore. Un URL come /watch?v=abc123 usa v per scegliere un video: non occorre un form. La presenza della query non dice se la risposta sia statica o dinamica. Anche richieste con altri metodi, per esempio POST, possono avere parametri nell’URL: query e body sono parti distinte.

Perché separiamo req.url e pathname?

// Da leggere dentro la funzione del server:
const url = new URL(req.url, `http://${IP}:${PORT}`);

// Con la richiesta /saluto?nome=Ada&classe=4A:
// req.url                         -> '/saluto?nome=Ada&classe=4A'
// url.pathname                    -> '/saluto'
// url.search                      -> '?nome=Ada&classe=4A'
// url.searchParams.get('nome')     -> 'Ada'
// url.searchParams.get('classe')   -> '4A'

Confrontare req.url === '/saluto' fallirebbe quando sono presenti parametri. Confrontare url.pathname === '/saluto' permette di riconoscere la rotta; url.searchParams permette poi di leggere i dati separatamente. get restituisce una stringa oppure null se il parametro manca: anche ?pagina=2 fornisce il testo “2”, non un numero JavaScript.

La base di new URL. Node riceve normalmente un percorso come /saluto?nome=Ada, che da solo non è un indirizzo completo. Il secondo argomento fornisce schema e host per interpretarlo. Il precedente 'http://localhost' era soltanto una base di analisi: new URL non apre una connessione e non avvia un altro server. Qui usiamo `http://${IP}:${PORT}` per renderla coerente con gli esempi. È sempre listen(PORT, IP, ...) a stabilire dove ascolta il server.

Spazi, accenti e simboli dentro un valore

Se il nome è “Ada Lovelace”, il browser deve rappresentare anche lo spazio. I form GET usano la codifica dei form: gli spazi diventano +. Uno spazio può anche essere rappresentato con %20. Il simbolo % introduce una sequenza di codifica; non significa “percentuale”:

/saluto?nome=Ada+Lovelace&classe=4A
/saluto?nome=Ada%20Lovelace&classe=4A

In entrambi i casi url.searchParams.get('nome') restituisce “Ada Lovelace”. Per distinguere un carattere contenuto nel dato da un separatore, usiamo la sua forma codificata:

Dato da trasmettereNel valore dell’URLPerché
Ada & Gracenome=Ada+%26+Grace%26 è una & contenuta nel nome, non un nuovo parametro.
C++corso=C%2B%2B%2B rappresenta un + letterale, senza scambiarlo per uno spazio.
C#corso=C%23%23 rappresenta il carattere # come dato.
50%sconto=50%25%25 rappresenta il simbolo % stesso.
caffètesto=caff%C3%A8Gli accenti vengono codificati usando i byte UTF-8.

Non serve comporre queste sequenze a memoria. Il browser codifica i campi del form; in JavaScript puoi far costruire i parametri a URLSearchParams:

const parametri = new URLSearchParams({ nome: 'Ada & Grace', corso: 'C++' });
console.log(parametri.toString());
// nome=Ada+%26+Grace&corso=C%2B%2B

Il + non significa spazio in ogni punto di qualsiasi URL: questa interpretazione riguarda i parametri nella codifica dei form e la loro lettura con URLSearchParams. La codifica rende rappresentabili i caratteri: non nasconde e non cifra i dati. I parametri restano nell’indirizzo e possono finire nella cronologia o nei log, quindi qui usiamo soltanto dati di esempio.

Altri caratteri da riconoscere: /, : e #

http://127.0.0.1:3000/saluto?nome=Ada&classe=4A#risultato
ParteSignificato
http: e //Lo schema e l’inizio della parte che contiene l’host.
:3000I due punti dopo l’host introducono la porta.
/salutoIl percorso. Gli slash separano i suoi segmenti, per esempio /corsi/node.
?nome=Ada&classe=4ALa query viene inviata al server insieme al percorso.
#risultatoIl frammento resta nel browser: può indicare un elemento della pagina a cui scorrere. Non viene inviato nella richiesta HTTP.

Con quell’indirizzo il server riceve /saluto?nome=Ada&classe=4A: in req.url non compare #risultato. Se invece # deve far parte del dato, va codificato come %23, come nell’esempio del corso C#.

Prova guidata: un form GET con due campi

È una piccola variante indipendente della tappa 7. Sostituisci tutto server.cjs con questo esempio completo e riavvia. Qui gestiamo solo la home e /saluto; i contatti torneranno nel progetto della tappa 8. Non servono script nel frontend.

    <p><label>Nome: <input name="nome" value="Ada"></label></p>
    <p><label>Classe: <input name="classe" value="4A"></label></p>
    <button type="submit">Chiedi il saluto</button>
  </form>
</body>
</html>`);
    return;
  }

  if (url.pathname === '/saluto') {
    const nome = url.searchParams.get('nome') || 'ospite';
    const classe = url.searchParams.get('classe') || 'non indicata';
    res.writeHead(200, { 'Content-Type': 'text/plain; charset=utf-8' });
    res.end('Ciao, ' + nome + '! Classe: ' + classe);
    return;
  }

  res.writeHead(404, { 'Content-Type': 'text/plain; charset=utf-8' });
  res.end('Pagina non trovata.');
});

server.listen(PORT, IP, () => {
  console.log(`Server attivo su http://${IP}:${PORT}`);
});

Apri la home e invia il form. Poi confronta queste prove, senza modificare il server:

curl.exe -i "http://127.0.0.1:3000/saluto?nome=Ada&classe=4A"
curl.exe -i "http://127.0.0.1:3000/saluto?nome=Ada%20Lovelace&classe=4A"
curl.exe -i "http://127.0.0.1:3000/saluto?nome=Ada%20%26%20Grace&classe=4A"
curl.exe -i http://127.0.0.1:3000/saluto

Risultato atteso. Nell’ordine ricevi “Ciao, Ada! Classe: 4A”, “Ciao, Ada Lovelace! Classe: 4A”, “Ciao, Ada & Grace! Classe: 4A” e “Ciao, ospite! Classe: non indicata”. Tutte sono GET sulla stessa rotta /saluto; cambiano i parametri e quindi il testo prodotto dal nostro programma. Usa le virgolette nei comandi per evitare che la shell interpreti & come un proprio simbolo.

Tocca a te. Inserisci nel form “Ada & Grace”: osserva l’URL generato e il nome ricostruito nella risposta. Poi inverti l’ordine di nome e classe nell’URL: il programma continua a leggerli per nome. Aggiungi #prova nella barra del browser e controlla in Network che il frammento non sia stato inviato. Per approfondire: se scrivi ?nome=Ada&nome=Grace, get restituisce il primo valore; getAll permette di leggerli entrambi.

Approfondimenti: le parti di un URL, URLSearchParams e codifica dei valori, il metodo GET.

server.cjs · versione 7

const http = require('node:http');
const fs = require('node:fs');
const path = require('node:path');

const IP = '127.0.0.1';
const PORT = 3000;

const server = http.createServer((req, res) => {
  if (req.method !== 'GET') {
    res.writeHead(405, { 'Content-Type': 'text/plain; charset=utf-8', 'Allow': 'GET' });
    res.end('Metodo non consentito. Usa GET.');
    return;
  }

  const pathname = new URL(req.url, 'http://localhost').pathname;

  if (pathname === '/') {
    const filename = path.join(__dirname, 'public', 'index.html');
    fs.readFile(filename, (error, content) => {
      if (error) {
        console.error(error);
        res.writeHead(500, { 'Content-Type': 'text/plain; charset=utf-8' });
        res.end('Il server non riesce a leggere il file.');
        return;
      }
      res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' });
      res.end(content);
    });
    return;
  }

  if (pathname === '/saluto') {
    res.writeHead(200, { 'Content-Type': 'text/plain; charset=utf-8' });
    res.end('Ciao dalla rotta /saluto!');
    return;
  }

  if (pathname === '/contatti') {
    res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' });
    res.end('<h1>Contatti</h1><p>Scrivi al docente.</p><a href="/">Torna alla home</a>');
    return;
  }

  res.writeHead(404, { 'Content-Type': 'text/plain; charset=utf-8' });
  res.end('Pagina non trovata.');
});

server.listen(PORT, IP, () => {
  console.log(`Server attivo su http://${IP}:${PORT}`);
});

__dirname è la cartella del file server.cjs; path.join costruisce il percorso sul disco anche su Windows. La funzione (error, content) => { ... } è una callback: Node la esegue quando la lettura termina. Prima controlliamo error; se non c’è, inviamo content. Non occorre async/await.

Risultato atteso. Il sito si comporta come prima. Cambia l’h1 in public/index.html e ricarica: vedrai la nuova scritta perché il server rilegge il file. Se cambi server.cjs, invece, devi riavviare Node. Rinomina temporaneamente index.html: GET / restituisce 500; poi ripristinalo.

Tocca a te. Sposta anche la pagina dei contatti in public/contatti.html e servila con lo stesso schema. Non usare req.url come percorso libero del disco: scegli esplicitamente quali file esporre.

const path = require('node:path');

const PORT = 3000;

      res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' });
      res.end(content);
    });
    return;
  }

  if (pathname === '/immagine') {

    fs.readFile(filename, (error, content) => {
      if (error) {

        return;

      res.writeHead(200, { 'Content-Type': 'image/png' });
      res.end(content);
    });
    return;
  }

Il browser chiede prima GET / per l’HTML, poi GET /immagine perché incontra il tag img. Il server legge foto.png come byte e li invia con Content-Type: image/png. Non convertire i byte in una stringa UTF-8.

File realeContent-Type
foto.pngimage/png
foto.jpg oppure foto.jpegimage/jpeg
foto.gifimage/gif
foto.webpimage/webp

L’immagine può essere di un altro tipo: sostituisci il file e cambia sia il nome nel path.join sia il Content-Type. Rinominare una PNG in .jpg non la converte. Il precedente image/svg+xml era il tipo specifico di SVG, un formato descritto con XML: lo lasciamo come curiosità, non come requisito di questo laboratorio.

Prova nel secondo terminale

curl.exe -o foto-ricevuta.png http://127.0.0.1:3000/immagine

Risultato atteso. Nella home vedi immagine, link e pulsante. Aprendo /immagine vedi la sola immagine. In Network la risposta dell’immagine è 200 image/png. Il comando salva una copia dell’immagine in foto-ricevuta.png: aprila per controllarla. Gli header si leggono nella scheda Network. Se manca foto.png ottieni 500; /sconosciuta dà 404.

Tocca a te. Usa una vera foto JPEG e cambia il MIME in image/jpeg. Il percorso pubblico può restare /immagine. Spiega la differenza tra quel percorso e public/foto.jpg sul disco.
