System Design · EventiScuola

Dati, transazioni e concorrenza

Dal server unico al database

All'inizio EventiScuola potrebbe essere eseguito interamente su un solo computer.

             UTENTI
                |
                v
       +-----------------+
       |     SERVER      |
       |-----------------|
       | Applicazione    |
       | Database        |
       | File e immagini |
       +-----------------+

Questa architettura è semplice da configurare e mantenere, ma presenta alcuni limiti.

Se il computer si guasta, il servizio smette di funzionare. Se vengono eseguite troppe operazioni, applicazione e database competono per le stesse risorse.

Una possibile evoluzione consiste nel separare il server applicativo dal database.

   CLIENT
      |
      v
+----------------+
| SERVER WEB /   |
| APPLICATIVO    |
+----------------+
      |
      v
+----------------+
| SERVER         |
| DATABASE       |
+----------------+

I due componenti svolgono funzioni differenti:

Server applicativo: esegue le regole del servizio.

Database server: memorizza i dati ed esegue le operazioni necessarie per recuperarli o modificarli.

La separazione consente anche di potenziare i due sistemi indipendentemente.

Progettazione dei dati: Data Modeling

Prima di scegliere un database bisogna stabilire quali informazioni memorizzare e quali relazioni esistono tra esse.

Per EventiScuola possiamo individuare queste entità:

Entità Dati principali
Utenti ID, nome, email
Eventi ID, titolo, data, luogo
Posti ID, evento associato, numero
Prenotazioni ID, utente, posto, stato
Pagamenti ID, prenotazione, importo, stato

La tabella Prenotazioni collega un utente a un posto.

Per esempio:

ID prenotazione ID utente ID posto Stato
1 103 42 Confermata
2 105 47 Confermata

È importante assegnare identificatori alle entità, perché permettono di collegare informazioni senza doverle duplicare inutilmente.

SQL e database relazionali

I database relazionali organizzano le informazioni in tabelle composte da righe e colonne.

Utilizzano SQL (Structured Query Language) per interrogare e modificare i dati.

Tra gli esempi più diffusi ci sono PostgreSQL, MySQL e SQLite.

Un vantaggio importante è la possibilità di rappresentare relazioni tra entità differenti e recuperare informazioni mediante operazioni come le JOIN.

Per esempio:

SELECT Utenti.nome, Prenotazioni.id
FROM Utenti
JOIN Prenotazioni
ON Utenti.id = Prenotazioni.utente_id;

La query collega le prenotazioni agli utenti che le hanno effettuate.

NoSQL

NoSQL identifica una famiglia di database che utilizzano modelli differenti da quello relazionale tradizionale.

Alcune categorie sono:

Categoria Modello Esempio
Documentale Documenti simili a JSON MongoDB
Chiave-valore Associazione chiave e valore Redis
Wide-column Dati organizzati per partizioni e colonne Cassandra
A grafo Nodi e relazioni Neo4j

Un database documentale potrebbe memorizzare un evento e alcune informazioni correlate all'interno di un unico documento.

Un database chiave-valore potrebbe invece associare un identificatore di sessione alle informazioni necessarie per riconoscere un utente.

La scelta non dipende semplicemente dal fatto che i dati siano strutturati o meno. Bisogna considerare anche le operazioni richieste, le relazioni, i vincoli di integrità, il volume dei dati e le esigenze di scalabilità.

I database SQL moderni possono inoltre gestire documenti JSON e grandi quantità di dati; alcuni database NoSQL offrono transazioni.

Transazioni e proprietà ACID

Consideriamo un problema fondamentale per EventiScuola.

Il posto B12 è libero. Due utenti tentano di acquistarlo nello stesso momento.

Se entrambe le richieste leggono che il posto è libero e poi registrano due prenotazioni, il sistema vende due volte lo stesso posto.

Per evitare situazioni simili sono necessari controlli di concorrenza, vincoli e transazioni.

Una transazione è un insieme di operazioni che il database gestisce come un'unità logica.

Le proprietà fondamentali sono rappresentate dall'acronimo ACID.

Proprietà Significato
A — Atomicity Tutte le operazioni della transazione vengono confermate oppure annullate
C — Consistency La transazione rispetta i vincoli di integrità definiti
I — Isolation Le transazioni concorrenti vengono controllate secondo un livello di isolamento
D — Durability I dati confermati sopravvivono ai guasti previsti dal sistema di persistenza

Per la prenotazione del posto B12:

  1. Il database verifica che il posto possa essere assegnato.
  2. Registra la prenotazione.
  3. Segna il posto come occupato.
  4. Conferma le modifiche come una singola transazione.

In alternativa, un vincolo di unicità sul posto prenotato può impedire la creazione di due prenotazioni attive per lo stesso posto.

Le operazioni concorrenti devono essere coordinate: non basta eseguire una semplice lettura e poi una scrittura senza controlli.

Questo è un esempio di come la correttezza del sistema sia importante quanto la velocità.
