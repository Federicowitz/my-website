Dal server unico al bilanciamento

Come si misurano le prestazioni?

Prima di migliorare un sistema bisogna capire che cosa lo rallenta.

Tre concetti fondamentali sono latenza, throughput e bandwidth.

Latenza

La latenza indica il tempo impiegato da un'operazione, per esempio quanto passa tra l'invio di una richiesta e il ricevimento della risposta.

Una richiesta che impiega 200 ms ha una latenza inferiore rispetto a una che richiede 3 secondi.

Throughput

Il throughput misura la quantità di lavoro completata nell'unità di tempo.

Per un server si potrebbe misurare in richieste completate al secondo.

Un sistema in grado di rispondere a 1.000 richieste al secondo ha un throughput superiore a uno che ne completa 100, se confrontato nello stesso contesto.

Bandwidth

La larghezza di banda rappresenta la capacità di trasmissione del collegamento, tipicamente misurata in bit al secondo.

Non va confusa con il throughput applicativo.

Un collegamento molto veloce non rende necessariamente veloce un'applicazione, perché la richiesta potrebbe essere rallentata dal database o dalle elaborazioni del server.

Il bottleneck

Un bottleneck è un collo di bottiglia, cioè il componente che limita le prestazioni complessive.

Per esempio, potrebbe essere il processore del server, il database o un collegamento di rete.

La soluzione dipende da dove si trova il problema: potenziare la CPU non risolve una query SQL particolarmente inefficiente.

Nell'analisi delle prestazioni si usano anche i percentili. Il P99 indica un valore di latenza entro cui si conclude circa il 99% delle richieste osservate.

Scalabilità verticale e orizzontale

Immaginiamo che EventiScuola possa gestire 500 richieste al secondo, ma durante l'apertura delle prenotazioni ne arrivino molte di più.

Una possibile soluzione è aumentare la capacità di elaborazione.

Esistono due strategie principali.

Scaling verticale

Un server più potente

Aumento di CPU, RAM e altre risorse

Scaling orizzontale

Più server

Distribuzione del lavoro tra più macchine

Scaling verticale (scale up): si potenzia una macchina aggiungendo risorse.

È relativamente semplice, ma ogni server ha limiti hardware ed economici.

Scaling orizzontale (scale out): si aggiungono altre macchine che collaborano per gestire il carico.

Questa soluzione può fornire maggiore capacità e ridondanza, ma richiede coordinamento.

Le due tecniche possono essere combinate. Lo scaling orizzontale non elimina automaticamente ogni problema di disponibilità: occorre verificare anche database, reti e componenti condivisi.

Il Load Balancer: distribuire le richieste

Supponiamo che EventiScuola utilizzi tre server applicativi identici.

Quando arriva una richiesta, quale server deve occuparsene?

Serve un componente che distribuisca il traffico: il Load Balancer.

Il load balancer riceve il traffico e lo inoltra ai server applicativi disponibili.

Il load balancer permette di distribuire le richieste su più server e, se opportunamente configurato, evita di inviarne di nuove a quelli non funzionanti.

Algoritmi di bilanciamento

Algoritmo Funzionamento Quando è utile
Round Robin Distribuisce le richieste a rotazione Server simili
Least Connections Sceglie il server con meno connessioni attive Connessioni di durata variabile
Least Response Time Considera i tempi di risposta, spesso insieme al carico Server con prestazioni differenti
Weighted Round Robin Distribuisce in base a pesi assegnati Server di diversa capacità
IP Hash Associa un client a un server usando l'IP Affinità di sessione
Geografico Seleziona infrastrutture in base alla posizione Servizi distribuiti globalmente
Consistent Hashing Utilizza uno spazio hash per assegnare elementi ai nodi Distribuzione con cambiamenti relativamente limitati delle assegnazioni

Per esempio, con Round Robin:

Richiesta 1 → Server A
Richiesta 2 → Server B
Richiesta 3 → Server C
Richiesta 4 → Server A
Richiesta 5 → Server B

Il sistema non controlla necessariamente quale server sia meno occupato: segue una rotazione.

Health Check

Come può il load balancer sapere se un server funziona?

Può eseguire controlli periodici detti health checks.

Se il server B non risponde correttamente, viene temporaneamente escluso dalle nuove richieste.

Quando torna disponibile, può essere reinserito.

Questo meccanismo migliora la tolleranza ai guasti, ma non garantisce che una richiesta già in corso non venga interrotta.

Load Balancer e Reverse Proxy

Un reverse proxy riceve richieste per conto dei server posti dietro di esso.

Può occuparsi, ad esempio, di terminazione HTTPS, inoltro delle richieste, controllo degli accessi o cache.

Un load balancer può operare come reverse proxy, ma i due concetti non sono sinonimi: il reverse proxy è un ruolo più generale.

Esempi di software utilizzati per queste funzioni sono Nginx e HAProxy; esistono anche servizi gestiti dai provider cloud.

È importante non confondere il load balancing applicativo con il routing IP.

Il router decide come inoltrare i pacchetti verso reti di destinazione. Il load balancer decide come distribuire traffico o richieste tra risorse che forniscono un servizio.

Stateful e Stateless: che cosa succede alle sessioni?

Aggiungere più server introduce un problema meno evidente.

Immaginiamo che un utente effettui il login e che la richiesta venga gestita dal server A.

Se A memorizza la sessione nella propria memoria, una richiesta successiva indirizzata al server B potrebbe non essere riconosciuta.

Il risultato sarebbe un utente che viene disconnesso casualmente.

Server stateful

Un server è stateful quando conserva informazioni necessarie a interpretare le interazioni successive.

Per esempio, una sessione utente salvata soltanto nella RAM del server.

Server stateless

Un server applicativo è stateless rispetto alle richieste quando non dipende da uno stato conversazionale custodito esclusivamente nella propria memoria locale.

Le informazioni necessarie possono essere contenute nella richiesta oppure archiviate in un sistema condiviso.

Una soluzione consiste nel salvare le sessioni in uno store accessibile a tutti i server.

                 CLIENT
                    |
                    v
             LOAD BALANCER
               /       \
              v         v
          SERVER A   SERVER B
              \         /
               v       v
              SESSION STORE
                 condiviso

A questo punto entrambi i server possono verificare la sessione, indipendentemente da quale abbia gestito il login.

Una possibile alternativa sono le sticky sessions, che cercano di indirizzare lo stesso utente allo stesso server.

Le sticky sessions possono essere pratiche in alcuni casi, ma creano dipendenze dall'istanza assegnata e possono rendere più difficile la distribuzione del carico.

Il principio generale è separare, quando opportuno, lo stato persistente dai server applicativi.
