Il contratto delle API

Che cos'è un'API?

Un'API (Application Programming Interface) definisce un insieme di regole che consentono a un programma di utilizzare le funzionalità di un altro programma.

Nel caso delle API web, queste regole specificano generalmente:

  • quali operazioni sono disponibili;
  • quali indirizzi o endpoint utilizzare;
  • quali dati inviare;
  • quale struttura avrà la risposta;
  • come vengono segnalati gli errori.

Si può immaginare un'API come il menu di un ristorante: indica ciò che può essere richiesto, senza dover conoscere come viene preparato.

Quando EventiScuola mostra un evento, il frontend non ha bisogno di conoscere come il backend memorizza le informazioni. Deve soltanto sapere quale richiesta inviare e quale risposta aspettarsi.

REST: risorse e metodi HTTP

REST (Representational State Transfer) è uno stile architetturale molto diffuso per realizzare API web.

Le risorse sono identificate tramite URL e le operazioni vengono rappresentate attraverso metodi HTTP.

Metodo Operazione tipica Esempio
GET Leggere GET /eventi
POST Creare POST /prenotazioni
PUT Sostituire PUT /eventi/42
PATCH Modificare parzialmente PATCH /eventi/42
DELETE Eliminare DELETE /prenotazioni/15

I metodi permettono di realizzare le operazioni CRUD: Create, Read, Update, Delete.

In REST si preferiscono URL basati sui nomi delle risorse.

È preferibile GET /eventi rispetto a /getEventi, perché il metodo HTTP esprime già l'azione da compiere.

Filtraggio, ordinamento e paginazione

Un'applicazione con migliaia di eventi non dovrebbe restituirli necessariamente tutti in una sola risposta.

Le API possono fornire meccanismi per selezionare i dati:

GET /eventi?citta=Milano

Restituisce soltanto gli eventi di Milano.

GET /eventi?sort=data

Richiede l'ordinamento per data, secondo le convenzioni stabilite dall'API.

GET /eventi?page=2&limit=10

Richiede una pagina di risultati contenente, al massimo, dieci eventi.

La paginazione riduce la quantità di informazioni trasferite ed evita di elaborare grandi elenchi non necessari.

Codici di stato HTTP

Codice Significato Esempio
200 OK Evento restituito correttamente
201 Created Prenotazione creata
204 No Content Eliminazione riuscita senza contenuto di risposta
400 Bad Request Dati inviati non validi
401 Unauthorized Autenticazione assente o non valida
403 Forbidden Operazione non autorizzata
404 Not Found Evento inesistente
409 Conflict Posto già prenotato
429 Too Many Requests Troppe richieste
500 Internal Server Error Errore interno del server
503 Service Unavailable Servizio temporaneamente non disponibile

Il principio di idempotenza

Un'operazione è idempotente quando eseguirla più volte produce lo stesso effetto sullo stato del sistema che eseguirla una sola volta.

Una richiesta GET è progettata per essere sicura e idempotente, pur potendo restituire dati diversi se il contenuto cambia nel frattempo.

Una richiesta PUT che imposta ripetutamente lo stesso valore è idempotente.

Una richiesta POST che crea una nuova prenotazione a ogni esecuzione, normalmente, non lo è.

Questa distinzione diventerà importante quando analizzeremo i pagamenti e i tentativi automatici di ripetere le richieste.

REST, GraphQL e gRPC

REST non è l'unico modo di progettare API.

REST

Espone risorse tramite URL e utilizza comunemente JSON come formato di risposta.

È adatto a numerose applicazioni web e mobile, grazie alla semplicità e all'integrazione con HTTP.

GraphQL

GraphQL permette al client di specificare esattamente quali dati desidera ricevere.

Per esempio:

query {
  evento(id: 42) {
    titolo
    data
    luogo
  }
}

Il server restituisce soltanto i campi richiesti, se previsti dallo schema e consentiti all'utente.

Questo può ridurre il trasferimento di informazioni superflue e, in determinate architetture, il numero di richieste necessarie.

GraphQL introduce però una maggiore complessità nella gestione delle query, delle autorizzazioni e della cache.

gRPC

gRPC è un framework di comunicazione remota, utilizzato soprattutto per le comunicazioni tra servizi.

Utilizza comunemente Protocol Buffers per serializzare i dati e HTTP/2 come trasporto.

Può offrire comunicazioni efficienti, contratti fortemente tipizzati e funzionalità di streaming.

Caratteristica REST GraphQL gRPC
Modello Risorse Query e schema Chiamate a procedure remote
Formato tipico JSON JSON Protocol Buffers
Utilizzo frequente Web e mobile Interfacce con esigenze di dati articolate Comunicazioni interne tra servizi
Vantaggio principale Semplicità Selezione precisa dei dati Efficienza e contratti tipizzati
Difficoltà Gestire risorse e versioni Controllare query complesse Tooling e compatibilità con i client

La scelta dipende dalle esigenze. Non esiste una tecnologia migliore in assoluto.
