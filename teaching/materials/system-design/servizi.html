Messaggi e servizi

Polling e WebSocket

Torniamo alla pagina di prenotazione.

Gli utenti vedono una mappa con i posti disponibili.

Quando qualcuno acquista il posto B12, sarebbe utile aggiornare immediatamente la schermata degli altri utenti.

Con il normale modello richiesta-risposta, una soluzione consiste nel far interrogare ripetutamente il server.

Questa tecnica prende il nome di polling.

Client → Server: Ci sono aggiornamenti?
Server → Client: No

Client → Server: Ci sono aggiornamenti?
Server → Client: No

Client → Server: Ci sono aggiornamenti?
Server → Client: Sì, B12 è occupato

Con migliaia di utenti, le richieste ripetute possono generare un carico considerevole.

WebSocket

WebSocket permette una comunicazione bidirezionale persistente tra client e server.

Una volta stabilita la connessione, il server può inviare messaggi al client senza aspettare ogni volta una nuova richiesta HTTP.

CLIENT                 SERVER
   |                      |
   |---- Connessione ---->|
   |<--- Conferma --------|
   |                      |
   |<--- B12 occupato ----|
   |<--- B13 occupato ----|
   |                      |

È utile per:

  • chat;
  • giochi multiplayer;
  • notifiche in tempo reale;
  • aggiornamenti dei posti;
  • dashboard con dati aggiornati frequentemente.

La connessione WebSocket consente aggiornamenti rapidi, ma la disponibilità visualizzata resta informativa: l'effettiva assegnazione di un posto deve essere verificata dal backend tramite operazioni atomiche.

Comunicazione sincrona e asincrona

Immaginiamo che, dopo una prenotazione, EventiScuola debba:

  1. registrare l'operazione;
  2. generare un biglietto PDF;
  3. inviare un'email;
  4. aggiornare le statistiche.

Non tutte le operazioni devono necessariamente terminare prima di rispondere all'utente.

Comunicazione sincrona: un componente attende il completamento dell'operazione richiesta.

Comunicazione asincrona: un componente avvia o registra un'attività che potrà essere eseguita successivamente.

Per esempio, la prenotazione può essere confermata senza attendere la conclusione dell'invio email.

Message Queue: le code di messaggi

Le message queue permettono di separare chi produce un'attività da chi la esegue.

Il producer genera un messaggio.

Il message broker riceve e gestisce i messaggi, che possono essere conservati in code o instradati verso diversi destinatari.

Il consumer, spesso chiamato anche worker, elabora i messaggi.

Se arrivano mille richieste di invio email, i messaggi possono accumularsi nella coda e i worker li elaborano secondo la capacità disponibile.

AMQP

AMQP (Advanced Message Queuing Protocol) è un protocollo per sistemi di messaggistica, utilizzato in prodotti come RabbitMQ.

Supporta diversi modelli di instradamento dei messaggi.

Pub/Sub

Nel modello Publish/Subscribe un componente pubblica un evento, mentre diversi servizi possono sottoscriverlo e riceverlo.

Per esempio, quando viene confermata una prenotazione, diversi componenti possono reagire allo stesso evento:

         PRENOTAZIONE CONFERMATA
                     |
                     v
                 EVENT BUS
                /    |    \
               v     v     v
            Email  Notifica Statistiche

Le code di lavoro e il modello Pub/Sub non sono identici: nel primo caso un'attività può essere assegnata a un worker, mentre nel secondo uno stesso evento può essere distribuito a più sottoscrittori.

Problemi introdotti dalle code

Anche una coda affidabile introduce nuovi problemi.

Un messaggio potrebbe essere elaborato, ma il worker potrebbe interrompersi prima di confermarne il completamento. Il messaggio potrebbe quindi essere consegnato nuovamente.

Per questo le operazioni eseguite dai worker devono spesso essere idempotenti, oppure progettate per gestire duplicati.

I messaggi che falliscono ripetutamente possono essere spostati in una Dead Letter Queue, destinata all'analisi dei problemi.

Webhook

Un webhook è un meccanismo che permette a un servizio di notificare un altro servizio tramite una richiesta HTTP quando si verifica un evento.

Per esempio, un provider di pagamento potrebbe notificare EventiScuola che un pagamento è stato completato.

Il server riceve la notifica, ne verifica l'autenticità e aggiorna lo stato della prenotazione.

Il webhook evita che il sistema debba continuamente interrogare il servizio esterno per sapere se ci sono novità.

Idempotenza nei pagamenti

Immaginiamo che un utente prema Paga, il pagamento vada a buon fine, ma la risposta non raggiunga il browser.

L'utente potrebbe riprovare.

Senza protezioni, potrebbe essere addebitato due volte.

Una soluzione consiste nell'utilizzare una idempotency key, cioè un identificatore univoco associato alla stessa operazione logica.

Se una richiesta viene ripetuta con la stessa chiave, il server può riconoscerla e riutilizzare il risultato precedente invece di creare una seconda operazione.

Servono anche controlli di concorrenza per impedire che richieste simultanee con la stessa chiave vengano elaborate entrambe.

Monolite e microservizi

Finora abbiamo parlato di più server, ma non necessariamente di più applicazioni.

Un unico programma può essere eseguito su numerosi server.

Questa distinzione è essenziale per comprendere la differenza tra monoliti e microservizi.

Architettura monolitica

In un'architettura monolitica le funzionalità principali appartengono a un'unica applicazione distribuita come unità.

Per esempio, gestione utenti, eventi, prenotazioni e notifiche potrebbero appartenere allo stesso programma.

Il monolite offre generalmente maggiore semplicità di sviluppo, test e distribuzione iniziale.

Un monolite può comunque essere replicato su più server.

Microservizi

In un'architettura a microservizi l'applicazione è suddivisa in servizi autonomi, ciascuno responsabile di specifiche funzionalità.

Per EventiScuola:

                 API GATEWAY
                      |
           +----------+----------+
           |          |          |
           v          v          v
       UTENTI      EVENTI    PRENOTAZIONI
       SERVICE     SERVICE      SERVICE
                                  |
                                  v
                              PAGAMENTI
                               SERVICE

Ogni servizio può essere sviluppato, distribuito e, quando possibile, dimensionato indipendentemente.

Confronto

Monolite Microservizi
Una principale unità applicativa Più servizi autonomi
Comunicazione interna spesso diretta Comunicazione frequentemente via rete
Distribuzione iniziale più semplice Distribuzione più complessa
Debugging generalmente più concentrato Necessario seguire operazioni tra servizi
Può essere replicato orizzontalmente Consente scaling indipendente dei singoli servizi
Adatto anche a sistemi importanti Utile quando esistono esigenze reali di autonomia

I microservizi non sono automaticamente migliori: aumentano le esigenze di monitoraggio, coordinamento, gestione degli errori e consistenza dei dati.

Spesso una buona strategia è partire con un monolite ben strutturato e separare i componenti quando emergono motivazioni concrete.

API Gateway

Quando un'applicazione è composta da molti servizi, non è conveniente che il client debba conoscere gli indirizzi di tutti.

Un API Gateway costituisce un punto d'ingresso comune.

Può svolgere diverse attività:

  • inoltrare le richieste ai servizi corretti;
  • verificare autenticazione e autorizzazioni preliminari;
  • applicare rate limiting;
  • raccogliere dati da più servizi;
  • gestire logging e controlli condivisi.

Il gateway non sostituisce necessariamente il load balancer.

Il load balancer distribuisce il traffico tra istanze di un servizio.

L'API gateway coordina l'accesso a API e servizi differenti.

Le due funzioni possono coesistere e, in alcuni prodotti, essere implementate dallo stesso componente.
