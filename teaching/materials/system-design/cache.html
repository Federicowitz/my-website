Indici, cache e distribuzione dei contenuti

Database Indexing: velocizzare le ricerche

Immaginiamo che EventiScuola contenga milioni di prenotazioni.

Quando un utente apre la pagina Le mie prenotazioni, il sistema deve trovare soltanto quelle associate al suo account.

Senza un indice adeguato, il database potrebbe dover esaminare un numero molto elevato di record.

Un indice è una struttura dati che consente di individuare più velocemente le informazioni.

È simile all'indice analitico di un libro: invece di sfogliare ogni pagina, si cerca l'argomento e si raggiunge direttamente la parte interessata.

Per esempio:

CREATE INDEX idx_prenotazioni_utente
ON Prenotazioni(utente_id);

L'indice può aiutare il database a trovare rapidamente le prenotazioni appartenenti a uno specifico utente.

Molti database relazionali utilizzano strutture come i B-tree per questo scopo.

Perché non creare un indice per ogni colonna?

Gli indici hanno un costo:

  • occupano spazio;
  • devono essere mantenuti quando i dati cambiano;
  • possono rallentare inserimenti e aggiornamenti;
  • non risultano utili allo stesso modo per tutte le query.

La scelta degli indici deve derivare dalle interrogazioni effettivamente eseguite e dall'analisi delle loro prestazioni.

Cache: evitare operazioni ripetute

Anche con gli indici, un database può essere sovraccaricato quando moltissimi utenti chiedono continuamente le stesse informazioni.

Supponiamo che un evento molto popolare venga consultato centinaia di migliaia di volte.

Il titolo, il luogo e la descrizione cambiano raramente. Interrogare il database per recuperare continuamente gli stessi dati può essere uno spreco di risorse.

Una soluzione è la cache.

La cache conserva copie di informazioni che possono essere recuperate rapidamente.

Nella strategia cache-aside, l'applicazione cerca prima il dato nella cache.

Se lo trova, si verifica un cache hit.

Se non lo trova, si verifica un cache miss: l'applicazione recupera il dato dal database e può inserirlo in cache per le richieste successive.

Un software molto utilizzato per realizzare cache è Redis.

TTL e invalidazione

La cache introduce un nuovo problema: il dato copiato potrebbe diventare obsoleto.

Per esempio, un evento cambia orario, ma la cache contiene ancora quello precedente.

Il TTL (Time To Live) indica per quanto tempo un elemento può rimanere nella cache prima di scadere.

Un'altra strategia è l'invalidazione attiva, con cui l'applicazione elimina o aggiorna la copia quando il dato originale cambia.

Per i dati poco critici può essere accettabile un breve ritardo.

Per informazioni come autorizzazioni, disponibilità effettiva dei posti e risultati dei pagamenti, è invece necessario adottare controlli più rigorosi.

La cache non dovrebbe essere considerata automaticamente la fonte definitiva della verità.

Cache Stampede

Se un elemento molto richiesto scade improvvisamente, migliaia di richieste potrebbero interrogare contemporaneamente il database per ricostruirlo.

Il fenomeno si chiama cache stampede.

Si può mitigare coordinando l'aggiornamento dell'elemento, anticipando il refresh oppure evitando scadenze simultanee di molti elementi popolari.

CDN: avvicinare i contenuti agli utenti

Una cache applicativa può ridurre il lavoro del database, ma non risolve necessariamente il problema della distanza geografica.

Se il server principale si trova in Europa e un utente accede dall'Australia, immagini e file potrebbero dover attraversare collegamenti molto lunghi.

Una CDN (Content Delivery Network) utilizza una rete di server distribuiti geograficamente per fornire contenuti da posizioni più vicine agli utenti.

I server edge mantengono copie dei contenuti e possono servirli agli utenti più vicini.

Quando un utente richiede un'immagine, la CDN verifica se il contenuto è disponibile sul server edge appropriato.

Se è presente, viene consegnato direttamente. Altrimenti, il server può recuperarlo dall'origine e conservarne una copia.

Cache e CDN non sono la stessa cosa

Cache applicativa CDN
Riduce soprattutto il lavoro ripetuto dei servizi e del database Riduce soprattutto la distanza e il carico di distribuzione dei contenuti
Può memorizzare risultati di query o dati applicativi Memorizza comunemente immagini, video, CSS, JavaScript e contenuti web
Può trovarsi vicino al backend Utilizza numerosi server geograficamente distribuiti

Entrambe sfruttano il riutilizzo di dati, ma rispondono a esigenze differenti.

Object Storage: dove salvare i file?

Un'applicazione può contenere molte immagini, video e documenti.

Memorizzare ogni file direttamente sul disco locale di un server applicativo crea problemi quando si utilizzano più server.

Se un utente carica un'immagine sul server A e la richiesta successiva raggiunge il server B, il file potrebbe non essere presente.

Una soluzione è utilizzare un servizio di Object Storage.

In questo modello i file vengono memorizzati come oggetti accessibili tramite identificatori.

Il database può conservare le informazioni relative al file e il riferimento all'oggetto.

DATABASE
Evento: 42
Titolo: Concerto di primavera
Poster: posters/evento42.jpg

OBJECT STORAGE
posters/evento42.jpg → contenuto immagine

Un esempio di servizio di object storage è Amazon S3.

La CDN può successivamente distribuire copie dei file conservati nell'object storage.
