System Design · EventiScuola

Dal requisito alla richiesta web

Introduzione: che cosa significa progettare un sistema informatico?

Quando utilizziamo un'applicazione come Instagram, Netflix, Amazon o un servizio di prenotazione online, vediamo soltanto la sua interfaccia: pagine, immagini, pulsanti e informazioni.

Dietro quell'interfaccia esiste però un insieme di componenti che collaborano per fornire il servizio.

Un'applicazione deve infatti essere in grado di:

  • ricevere le richieste degli utenti;
  • elaborarle;
  • memorizzare e recuperare dati;
  • comunicare con altri servizi;
  • rispondere velocemente;
  • gestire numerosi utenti contemporaneamente;
  • continuare a funzionare anche in presenza di guasti;
  • proteggere le informazioni.

La disciplina che studia come organizzare questi componenti prende il nome di System Design, ovvero progettazione dell'architettura di un sistema informatico.

Programmare e progettare un sistema non sono esattamente la stessa cosa.

Programmare significa realizzare le funzionalità di un'applicazione, scrivendo istruzioni che svolgono determinate operazioni.

Progettare l'architettura significa stabilire dove e come tali funzionalità devono essere eseguite, quali componenti devono collaborare e quali soluzioni adottare per soddisfare i requisiti del sistema.

Un esempio

Immaginiamo di sviluppare una piattaforma chiamata EventiScuola, che permette di consultare eventi, prenotare posti, acquistare biglietti e ricevere conferme.

All'inizio potrebbe essere sufficiente un computer che ospita sia l'applicazione sia il database.

Se però il servizio diventasse molto popolare, potrebbero presentarsi diversi problemi.

Problema Possibile soluzione
Troppi utenti contemporanei Aggiungere server e distribuire il traffico
Richieste molto lente Ottimizzare database e utilizzare una cache
Immagini lente da scaricare Utilizzare una CDN
Guasto del server principale Introdurre sistemi ridondanti
Database troppo grande Suddividere i dati mediante sharding
Notifiche che rallentano le prenotazioni Utilizzare code di messaggi
Due utenti acquistano lo stesso posto Utilizzare transazioni e vincoli di integrità
Accessi non autorizzati Autenticazione, autorizzazione e protezione delle API

Queste tecnologie non vengono introdotte tutte obbligatoriamente: ogni soluzione deve rispondere a un'esigenza reale.

Da dove si comincia? I requisiti del sistema

Prima di scegliere server, database o linguaggi di programmazione, bisogna stabilire che cosa deve fare l'applicazione e come deve comportarsi.

Esistono due categorie fondamentali di requisiti.

Requisiti funzionali

Descrivono quali operazioni il sistema deve consentire.

Per EventiScuola:

  • registrare un account;
  • effettuare il login;
  • visualizzare gli eventi;
  • consultare i posti disponibili;
  • prenotare un posto;
  • pagare un biglietto;
  • ricevere una conferma.

Se un utente non può prenotare un posto, manca una funzionalità richiesta.

Requisiti non funzionali

Descrivono le caratteristiche qualitative del sistema.

Ad esempio:

Requisito Significato
Prestazioni Le pagine devono caricarsi rapidamente
Scalabilità Il sistema deve gestire un numero crescente di utenti
Disponibilità Il servizio deve essere accessibile il più possibile
Affidabilità Le operazioni devono funzionare correttamente
Durabilità I dati salvati non devono scomparire dopo un guasto
Sicurezza I dati devono essere protetti
Manutenibilità Il sistema deve poter essere aggiornato e corretto
Costo Le risorse utilizzate devono essere economicamente sostenibili

Due applicazioni potrebbero offrire esattamente le stesse funzionalità, ma avere architetture molto differenti.

Una piattaforma utilizzata da 30 persone potrebbe funzionare perfettamente su un solo server. La stessa piattaforma, utilizzata da milioni di persone, potrebbe richiedere numerosi server, database distribuiti e sistemi di bilanciamento.

Due livelli di progettazione

Si distinguono inoltre:

High-Level Design (HLD): descrive i componenti principali e le loro interazioni. Per esempio, server applicativi, database, cache, load balancer e CDN.

Low-Level Design (LLD): descrive i dettagli interni di una funzionalità, come classi, metodi, strutture dati e algoritmi.

In questa lezione ci concentreremo soprattutto sull'High-Level Design.

L'architettura client-server

La maggior parte delle applicazioni web utilizza il modello client-server.

Il client è il dispositivo o programma che richiede un servizio. Il server è il sistema che riceve la richiesta, la elabora e restituisce una risposta.

Il client richiede una risorsa; il server elabora la richiesta e invia il risultato.

Immaginiamo che uno studente apra:

https://eventiscuola.example/eventi

Il browser invia una richiesta per ottenere l'elenco degli eventi. Il server riceve la richiesta, recupera le informazioni necessarie e restituisce una risposta.

Il server potrebbe inviare una pagina HTML oppure dati JSON che il browser utilizzerà per costruire l'interfaccia.

Frontend e backend

All'interno di un'applicazione web si distinguono spesso due parti.

Frontend Backend
È la parte con cui interagisce l'utente È la parte che gestisce le operazioni dell'applicazione
Mostra pagine, pulsanti e moduli Controlla dati, autorizzazioni e regole
Utilizza spesso HTML, CSS e JavaScript Può utilizzare Java, Python, JavaScript, PHP ecc.
Esegue codice nel browser Esegue codice sui server

Per esempio, quando si preme il pulsante Prenota, il frontend invia una richiesta al backend. Quest'ultimo verifica la disponibilità del posto e registra la prenotazione.

Un server non è necessariamente una macchina fisica dedicata: il software può essere eseguito anche su una macchina virtuale, in un container o tramite un servizio cloud.

Come fa il client a trovare il server? IP e DNS

I dispositivi che comunicano su una rete utilizzano indirizzi IP.

Un indirizzo IP identifica un'interfaccia di rete a livello IP e permette alla rete di instradare i pacchetti verso la destinazione.

Gli esseri umani, tuttavia, preferiscono ricordare nomi come eventiscuola.example piuttosto che indirizzi numerici.

Per questo esiste il DNS (Domain Name System), un sistema distribuito che consente di risolvere i nomi di dominio in informazioni di rete, tra cui gli indirizzi IP.

Come avviene una risoluzione DNS?

Il procedimento, semplificato, è questo:

  1. L'utente digita il dominio.
  2. Il dispositivo consulta il resolver DNS, eventualmente utilizzando una risposta già presente nella cache.
  3. Il resolver ottiene l'indirizzo IP associato al nome.
  4. Il client utilizza l'indirizzo per comunicare con la destinazione.
  5. La richiesta viene trasportata attraverso la rete fino al sistema che dovrà gestirla.

Il DNS non trasporta le pagine web: aiuta a individuare la destinazione.

È inoltre importante osservare che il dominio non deve necessariamente corrispondere direttamente all'indirizzo di un server applicativo. In architetture più complesse potrebbe corrispondere a un load balancer o a un'infrastruttura CDN.

Dai pacchetti di rete alle richieste web

Per comprendere come viaggiano le informazioni è utile ricordare che la comunicazione in rete è organizzata in livelli.

Livello OSI Esempi Funzione
7 — Applicazione HTTP, DNS, protocolli applicativi Definisce i servizi di comunicazione per le applicazioni
4 — Trasporto TCP, UDP Gestisce la comunicazione tra processi
3 — Rete IP Gestisce l'indirizzamento e l'instradamento
2 — Collegamento Ethernet, Wi-Fi Trasferisce i dati sul collegamento locale
1 — Fisico Cavi, fibre, segnali radio Trasmette i segnali

I livelli 5 e 6 del modello OSI sono stati omessi dalla tabella per concentrarsi su quelli più direttamente coinvolti negli esempi.

Il concetto fondamentale è che HTTP non sostituisce TCP, UDP o IP: questi protocolli svolgono funzioni differenti e collaborano.

TCP e UDP

TCP e UDP sono protocolli di trasporto.

TCP (Transmission Control Protocol) fornisce una comunicazione orientata alla connessione, con consegna ordinata e affidabile dei dati finché la connessione rimane operativa.

Prima dello scambio dei dati viene stabilita una connessione mediante il three-way handshake:

CLIENT                         SERVER

   -------- SYN -------------->
   <----- SYN + ACK -----------
   -------- ACK -------------->

       Connessione stabilita

TCP rileva le perdite, ritrasmette i dati necessari e li consegna all'applicazione nell'ordine corretto.

UDP (User Datagram Protocol) è invece privo di connessione e non implementa autonomamente meccanismi di ritrasmissione o ordinamento.

La minore complessità lo rende utile per applicazioni che gestiscono autonomamente la trasmissione o richiedono bassa latenza.

TCP UDP
Orientato alla connessione Senza connessione
Consegna ordinata Nessuna garanzia di ordine
Ritrasmissioni e controllo di flusso Non offre questi meccanismi autonomamente
Maggiore overhead Minore overhead di base
Utilizzato da molti servizi web Utilizzato in DNS, comunicazioni in tempo reale e altri servizi

Non è corretto affermare che UDP sia sempre più veloce di TCP. Le prestazioni dipendono anche dal protocollo applicativo e dalla rete.

Un esempio importante è HTTP/3, che utilizza QUIC, costruito sopra UDP, ma implementa comunque meccanismi di affidabilità e controllo della connessione.

HTTP e HTTPS

HTTP (Hypertext Transfer Protocol) è il protocollo applicativo utilizzato per scambiare richieste e risposte web.

Una richiesta potrebbe essere:

GET /api/v1/eventi/42 HTTP/1.1
Host: eventiscuola.example
Accept: application/json

La risposta:

HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 42,
  "titolo": "Concerto di primavera",
  "luogo": "Auditorium",
  "postiDisponibili": 57
}

La richiesta indica quale risorsa si desidera ottenere; la risposta fornisce il risultato e un codice di stato.

HTTPS è HTTP protetto tramite TLS, un protocollo crittografico che fornisce cifratura, integrità e autenticazione della controparte tramite certificati.

HTTPS protegge i dati durante il trasporto, ma non sostituisce il controllo degli accessi dell'applicazione.
